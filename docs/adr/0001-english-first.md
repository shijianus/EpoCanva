# ADR 0001 — 英文优先的语言顺序

## 状态

Accepted（基线决策）。P0.1 阶段仅落到文档与构建约束，未涉及任何实现。

**部分被取代（2026-11-05）**：语言优先级的**具体顺序**已由
[ADR 0005](0005-multilingual-language-profiles.md) 与
`docs/product/requirements.md` §3 取代为
`English > Chinese > French > Spanish > Japanese > Korean > German`。
本 ADR 的其余决策（英文优先的冲突裁决、英文是独立能力模块、禁止两种伪实现）
继续有效。按本 ADR 自身第 1 条，此次调整正是通过新 ADR 完成的。

## 背景

多数基于 librime 的输入法把英文当作"附加语言"处理：挂一个词典 Translator，
或者干脆把字母直通上屏。这使英文体验显著劣于系统自带键盘，也让 EpoCanva 失去差异化理由。

同时，EpoCanva 要以中文输入能力为基本盘（librime 的强项），并逐步支持法/日/韩。
不同语言在候选排序、编辑协议、学习特征空间上的需求并不一致，
因此需要一条明确的冲突裁决规则，而不是每次遇到问题临时协商。

## 决策

语言优先级固定为：

```
English > Chinese > French > Japanese > Korean > 通用 i18n
```

并且：

1. 该顺序不可由实现临时重排；调整必须走新的 ADR。
2. 当某个设计决策（Session 编辑协议、ABI 单位约定、候选编排框架、学习存储格式）
   对英文与其他语言不等价友好时，**以英文侧为准**。
3. 英文能力被定义为引擎内的独立模块（见 `docs/architecture/overview.md` 第 2.5 节），
   而不是词库配置项。
4. 明确排除两种"伪实现"：ASCII 直通；仅一个词典 Translator。
   二者均不构成需求满足，也不构成验收通过（见 `docs/product/requirements.md` 3.1）。
5. 因为英文优先，编辑协议必须能表达"提交后回改"（如 `teh` → 上屏后改成 `the`），
   这反过来约束了适配层能力，属于本决策的直接后果。

## 备选方案

| 方案 | 说明 | 未采纳原因 |
| --- | --- | --- |
| 中文优先，英文按需 | 沿用 rime 社区既有取向 | 产品定位即英文能力；既有取向已被市场验证为不足 |
| 语言并列、按用户设置排序 | 无固定优先级 | 架构分歧点仍需裁决者；"并列"实际等于由最省事的一侧决定 |
| 英文交给系统键盘，EpoCanva 只做中文 | 显著降低工程量 | 直接违背产品定位 |
| 以"多语言框架"起步，英文作为其中一个 locale | 抽象先行 | 会把英文的特殊需求（形态、纠错、回改）压成最小公倍数 |

## 后果

**正面**

- Session/编辑协议、ABI 单位约定、候选编排框架在设计时即面向最强需求，后期不为英文返工。
- 英文能力可作为独立可测模块演进，测试与验收条目清晰。

**负面 / 成本**

- 引擎复杂度显著高于"词典 + Translator"路线：分词、形态、纠错、切分都要自有实现。
- 中文侧若与英文侧共用候选编排框架，需额外保证不被英文特例污染。
- 每个语言的验收条目数量上升；早期阶段看起来"没有产出输入能力"。

**约束传导**

- 本 ADR 要求架构文档中把 `english-*` 与 `rime-adapter` 平级放置（已写入 overview.md）。
- 要求需求文档把"禁止 ASCII 直通 / 禁止单 Translator"列为验收不通过项（已写入 requirements.md）。

## 重新评估条件

出现以下任一情况时重新开启评估：

1. 英文能力模块连续两个阶段无法推进，且原因被证实是"英文优先"带来的架构约束，
   而非资源或排期。
2. 中文（或法/日/韩）侧出现英文无法满足的能力需求，形成实质互斥。
3. 出现经过验证的英文处理能力（如系统级建议、词法库）足以承担 3.1 中多数条目，
   使自研成本不再合理——注意：仅"词典查询"不足以触发本条。
4. 产品定位变更，EpoCanva 不再以英文为卖点。
