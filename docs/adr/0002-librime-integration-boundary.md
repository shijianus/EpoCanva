# ADR 0002 — librime 集成边界

## 状态

Accepted（边界定义）。P0.1 **未引入 librime**：本阶段禁止下载或 vendor 任何依赖，
本 ADR 只固定后续集成方式。

## 背景

librime 提供成熟的中文输入方案、词库编译与部署机制，是 EpoCanva 的引擎底座，
且项目允许源码级改造。但 librime 同时带来三个风险：

1. 它的 C++ 接口、内存所有权与线程/消息回调模型一旦被平台层直接依赖，
   改造与替换成本极高。
2. 小狼毫（Weasel）与同文（Trime）已经存在，如果沿用它们的集成方式，
   EpoCanva 会滑向"换皮发行"，这是需求文档明确禁止的。
3. 源码级改造若直接改在 `third_party/` 检出里，依赖将不可复现、不可校验、不可回退。

## 决策

1. **单一集成点**：只有 `rime-adapter` 模块可以 `#include <rime/...>` 并链接 librime。
   平台适配层（TSF / Android IME）与 engine-core 只见自有 C ABI。
2. **自有 C ABI**：`epocanva_engine.h` 定义 Session/编辑协议、句柄所有权、
   UTF-8 文本与**带单位**的偏移。librime 的类型、枚举与回调不得越过该边界。
3. **依赖锚点**：librime 以 `third_party/README.md` 的规则登记——完整 40 位 commit、
   SHA-256、许可证路径、允许被哪一层链接。禁止 FetchContent / 联网 clone。
4. **改造即补丁**：所有源码级修改以 `third_party/patches/NNNN-*.patch` 表达，
   上游检出保持字节干净；补丁清单与目的记录在 `docs/build/bootstrap.md`。
5. **行为差异隔离**：补丁引入的行为差异由 `rime-adapter` 吸收，不得要求平台层特判。
6. **参考而非继承**：Weasel / Trime 可作为"librime 在该平台上如何工作"的证据来源阅读，
   但其外壳、ABI、配置结构不作为 EpoCanva 的边界。

## 备选方案

| 方案 | 说明 | 未采纳原因 |
| --- | --- | --- |
| 平台层直接调用 librime C++ API | 工程量最小、上手最快 | 边界即失守；后续任何改造要改两处平台代码；换皮风险 |
| Fork librime 为自有仓库 | 改造自由 | 丢失上游可校验性，补丁不可枚举，安全更新难以回合 |
| 直接基于 Weasel/Trime 定制 | 可立刻得到可用产品 | 违反需求第 1 节"不换皮"；且其 ABI 非为英文能力设计 |
| 不用 librime，自研引擎 | 完全可控 | 放弃成熟的中文方案/词库编译生态，中文基本盘归零 |
| 用插件/DLL 动态装载 librime 接口 | 可热替换 | 跨 DLL 的 C++ ABI 稳定性问题，收益不抵风险 |

## 后果

**正面**

- librime 可被深度改造、甚至在远期替换，而不重写 TSF 与 Android 适配。
- 依赖可校验、可复现、可回退；许可证审计有单一入口。
- 英文能力模块有清晰的插入点，与 rime 路径共享 Session 而不共享语言学假设。

**负面 / 成本**

- 多一层 ABI 与适配器，早期工作量更大；P0.1 之后需要额外阶段专门实现边界。
- 自有 ABI 的设计错误会被两个平台同时放大，因此必须早期配对抗测试。
- 每次升级 librime 都要重跑补丁序列并重新校验哈希，维护成本显式存在。

**当前未实现**

- `rime-adapter`、`epocanva_engine.h` 均不存在；librime 未被下载。
- 本 ADR 的落地验证推迟到实际引入 librime 的阶段。

## 重新评估条件

1. librime 的接口模型使 `rime-adapter` 无法表达英文能力所需的候选编排
   （例如必须改内核数据结构才能插入自有 ranker）。
2. 源码级补丁累积到无法维护或相互冲突，说明"外部依赖"判断已不成立。
3. librime 上游许可证或分发条款发生变化。
4. 出现必须绕过 C ABI 才能达成的平台能力（如低延迟 preedit 更新），
   此时需重新评估边界粒度而不是默默打穿边界。
