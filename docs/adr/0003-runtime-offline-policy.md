# ADR 0003 — 运行期完全离线策略

## 状态

Accepted（策略与保证边界的定义）。P0.1 阶段只有工具链探针，
它**不读写用户目录、不联网、不读剪贴板**；本 ADR 约束的是后续所有运行期代码。

## 背景

输入法站在用户所有文本的最前端，任何联网与上报都是高敏感行为。产品决定运行期完全离线。

难点在于**两个平台的强制能力根本不同**，而文档必须诚实反映这一点：

- **Android**：权限在清单中声明。若 APK **不申请** `android.permission.INTERNET`，
  操作系统会在内核/系统调用层面阻止任何网络访问，这是平台强制的硬保证。
  代价是权限一旦声明即整体生效，无法按页面或按功能收回，所以只能"根本不声明"。
- **Windows**：TSF 组件是普通 DLL，被加载进用户正在使用的任意宿主进程
  （浏览器、编辑器、密码管理器）。Windows **没有**给这类进程内组件提供
  "禁用网络"的权限位或沙箱。因此：
  > 在 Windows 上，EpoCanva **不能承诺操作系统级别的网络阻断**。
  > 任何声称"Windows 上不可能联网"的表述都是错误的，文档、界面与对外承诺都不得出现。

## 决策

1. **运行期零网络**：EpoCanva 的任何运行期代码不得发起网络请求——
   无遥测、无崩溃上报、不接入任何 APM/Crash 服务 SDK、无静默更新、无云候选、无词库同步。
   更新检查（若未来需要）属于独立安装器/独立应用，与输入进程隔离，且必须是显式用户动作。
2. **不上传输入内容**：键入序列、组合缓冲、已上屏文本、剪贴板内容一律不出设备。
3. **日志最小化**：诊断日志只允许记录枚举值、计数器与不含用户内容的错误码。
   禁止记录按键码序列、preedit/commit 文本、字段名、窗口标题，
   也禁止记录它们的哈希或可逆编码（哈希在固定词表下可被反查，不构成脱敏）。
4. **隐私字段不学习**：密码、一次性验证码，以及被宿主或平台标记为敏感的字段，
   在**写入侧**即排除于学习模型与持久化之外，而非仅在读侧过滤。
5. **保证的表述方式（按平台分别措辞，禁止合并成一句"绝不联网"）**：
   - Android：平台强制。清单不含 `INTERNET` 权限，构建后有自动化检查核验合并清单。
   - Windows：架构与工程保证。由"自有代码与依赖不含 socket 调用"、
     依赖白名单审查、代码评审共同达成；它抵御的是"我们的代码去联网"，
     不抵御"已存在于宿主进程中的其他代码联网"。
     未来若加入链接/导入表检查，其覆盖面也**仅限静态导入**，
     不覆盖运行期动态加载，因此它只是纵深防御的一层，不是保证本身。
6. **可验证性优先于承诺**：策略必须落到可执行检查（依赖清单、符号/导入表审查、
   自动化用例），而不是只在文档里写一句声明。

## 备选方案

| 方案 | 说明 | 未采纳原因 |
| --- | --- | --- |
| 可选遥测，默认关闭 | 便于改进词库 | 输入法场景下"默认关闭"仍构成信任负担；用户无法验证 |
| 云候选/云同步 | 直接提升英文长尾质量 | 违背产品核心承诺；且把隐私字段暴露风险引入所有输入路径 |
| 在 Windows 上用沙箱/独立进程承载引擎 | 有望取得 OS 级隔离 | 与 TSF 的进程内模型冲突：文本编辑必须由宿主进程内的调用完成；跨进程 IPC 另需威胁建模（见 threat-model 第 5 节） |
| 用 AppContainer / 打包约束 DLL | 似乎可加权限位 | 普通桌面 TSF 组件不属于 MSIX 打包应用，无法据此获得网络阻止；不得以此对外承诺 |
| 崩溃上报仅发送堆栈不发送文本 | 折中 | 堆栈与内存快照在输入法中不足以与用户内容解耦 |

## 后果

**正面**

- 隐私承诺简单、可审计、可对外解释；Android 侧有平台背书。
- 运行期不引入网络依赖，减少许可与供应链面。
- 英文/中文词库必须在本地达成质量目标，倒逼能力层自研而非"加一个云接口"。

**负面 / 成本**

- 无法用云端数据改进质量，词库与模型的改进只能靠发行包更新。
- Windows 侧无法给出强技术保证，需要长期维持导入表/依赖审查流程；
  一旦出现第三方插件，该保证的强度进一步下降。
- 无遥测意味着问题诊断依赖用户主动导出日志，日志格式必须预先设计成"不含用户内容"。

**当前验证状态**

- P0.1 做到的只是：探针的代码路径不含任何网络调用、不读写用户目录，
  且本阶段没有引入任何依赖。这是**代码审查层面**的结论。
- P0.1 观测到的 PE 依赖信息（`dumpbin /dependents`）不足以支撑任何离线承诺，
  此前把它表述为"已验证不产生网络行为"**属于过度声称，现予撤回**：
  PE 导入表只能说明"该二进制没有静态导入网络 API"，
  既不能覆盖运行期动态加载（`LoadLibrary`/`GetProcAddress`）的路径，
  也不能覆盖宿主进程中其他模块的行为，更不能外推到尚未存在的引擎与适配层。
  不同构建选项下依赖列表本身就会变（手工 `cl` 产物只列 `KERNEL32.dll`，
  CMake `/MDd` 产物另列 4 个 CRT DLL），可见它是构建标志的函数，不是安全属性。
- P0.1 **未实现**：Android 合并清单权限检查、日志内容合规用例、
  任何自动化网络守卫。这些属于后续阶段，不得声称已存在。
- 导入表/链接检查**不作为 P0.1 的完成条件**；它将在依赖真正引入后再作为
  纵深防御的一层设计，且即便如此也只是"静态入口"层面的一层。

## 重新评估条件

1. 出现必须联网才能达成的核心功能，且该产品决策被上层重新确认（此时本 ADR 需 Superseded）。
2. Windows 平台提供适用于 TSF 组件的网络约束机制，使"架构保证"可升级为"平台强制"。
3. 离线词库质量长期无法达到英文能力目标，需要在"云端能力"与"本地更大模型"之间重新权衡。
4. 引入外部插件机制，导致"依赖不含 socket 调用"这一前提不再由 EpoCanva 单方控制。
