# Language Package Contract

EpoCanva treats a language package as a declared capability boundary, not as a synonym for a dictionary or a release approval. The C++ contract lives in `engine/language_packages/language_package.h` and has no filesystem, network, deployment, or certificate side effects.

Each manifest has one exact language identity (`en`, `zh`, `fr`, `ja`, or `ko`), one safe schema identifier, UTF-8 display label, input/output modes, required built-in module names, capability declarations, data resources, and an explicit readiness record. Language priority is fixed as English, Chinese, French, Japanese, Korean. A catalog rejects duplicate language or schema identities. Modules are an allowlist of compiled-in names; paths, plugin names, directory discovery, and external module loading are never accepted.

A capability lists every resource it requires. A declared dictionary, frequency file, morphology source, or conversion model is not silently replaced with an empty table or a fixed candidate list. `AdmitCapabilities` consumes verifier-supplied evidence containing exact source identity, revision, SHA-256, license reference, and approval scope. The contract compares these values; it does not claim to audit a license or grant redistribution rights. Missing or unapproved data refuses the dependent capability while allowing an independently implemented composition or phonetic-analysis capability to remain explicitly partial.

The current product policy intentionally keeps the default schema English-only. The language readiness manifest requires all five languages for aggregate delivery, and currently records English as incomplete and Chinese, French, Japanese, and Korean as blocked for product packaging. The standalone cores are therefore testable engineering components, not shipped language profiles. Chinese phonetic analysis does not claim Hanzi, phrase, frequency, or traditional/simplified conversion. Japanese Romaji/Kana does not claim Kana-to-Kanji. Korean Jamo/Hangul composition does not claim Hanja or lexical prediction. French accent composition does not claim a production lexicon, full Unicode NFC/UAX #29, gender/POS inference, or morphology completeness.

The Windows bridge keeps the existing English default. `RuntimeOptions.required_modules` defaults to `epocanva_english`; the runtime always requests `default` (the pinned librime group loads `core`, `dict`, and `gears`), then appends only approved requested modules and deployment-only `levers`. It validates requested names before loading, verifies each requested module through librime's `find_module`, and runs the English custom API compatibility check only when English was requested. The implementation was checked against the pinned librime revision `33e78140250125871856cdc5b42ddc6a5fcd3cd4`: `src/rime/setup.cc` module loading, `src/rime_api_impl.h` initialization/finalization, `src/rime_api.cc` registration lookup, and `rime_api.h` module/custom API declarations.

This source-level module contract does not prove that a DLL contains a requested module, prove data licensing, or make a language product ready. The loaded DLL identity, source receipt, data hashes, privacy checks, TSF behavior, installation lifecycle, and aggregate host evidence remain separate gates.

Runtime code performs no network I/O. A normal Windows TSF DLL runs in its host process and is not OS network-sandboxed; the offline statement is architectural and depends on code/dependency review and build policy. A future Android artifact could receive platform-enforced offline behavior by omitting `android.permission.INTERNET`; no Android artifact is claimed here.
