## 3. 关键设计选择

### 3.1 探针只做四件事，并显式声明它不做什么
`main.cc` 顶部注释即边界声明：不读用户输入/剪贴板/文档/注册表/网络，不写任何位置。
`docs/product/requirements.md` 第 6 节与 AGENTS.md 第 3 条都把
"字节级 UTF-8 检查 ≠ Unicode 合规 ≠ 输入法能力"写成验收口径，防止后续误读。

检查项：
1. `CheckLanguageLevel`：`__cplusplus >= 201703`（static_assert + 运行期），捕获 `/Zc:__cplusplus` 缺失或被降级。
2. `CheckStdlibFeatures`：`std::optional`、`std::string_view`、结构化绑定、
   `if`-带初始化器、`constexpr` 变量、折叠表达式模板 —— 验证后续引擎层真正依赖的 C++17 面。
3. `CheckUtf8Bytes`：9 条**硬编码转义字节**样本（é/Ä/中/国/か/ミ/한/€/🤠），
   断言字节长度并校验 lead/continuation 结构。
   刻意用 `"\xC3\xA9"` 而非字面字符，使检查**不受源文件编码与编辑器影响**
   —— 这也让 `.gitattributes` 的换行/编码归一化不可能悄悄改掉测试向量。
4. `CheckDigest`：对固定内嵌字符串做 FNV-1a-64，与钉住的常量比对。

### 3.2 退出码分级，而不是笼统返回 1
`0/1/2/3/4/5/9` 分别对应 成功/语言级别/标准库特性/UTF-8 字节/摘要/用法/强制失败。
这样 CTest 的负向用例能区分"探针拒绝运行"与"探针检查不通过"。

### 3.3 测试必须能失败（三次实证）
- `forcefail` 模式与 `unknown mode` 模式各配一条 `WILL_FAIL TRUE` 用例；
  若测试桩退化成无条件成功，这两条会立刻转红。
- 正向用例用 `PASS_REGULAR_EXPRESSION "RESULT PASS"` 而非仅看退出码，
  防止"提前 return 0"冒充通过；另加 `FAIL_REGULAR_EXPRESSION "^FAIL "`。
- **实测证明**：把钉住的摘要常量末位改一个 nibble 生成一份临时副本（源码未动，副本在 `build/` 下），
  该副本以 **exit 4** 报 `FAIL digest-mismatch expected=ab47508aa940dbc1 actual=ab47508aa940dbc0`。

### 3.4 摘要值来自独立实现交叉核对（并纠正了我自己的两处错误）
期望常量最初凭推算写成 `0xB0A90A4A6E0AC56B`，随后又误记为 `0x034A803892095098`；
用 Node/BigInt 独立计算得 `0xab47508aa940dbc0` 后修正。
第一次真实运行还暴露出 `CheckStdlibFeatures` 里一条自相矛盾的断言
（`optional{1}` 却拿去和 `42+1` 比），探针以 **exit 2** 如实报错——
这正是"探针不是装饰"的证据。修 print 逻辑时发现 `Hex64` 把每字节两个 nibble 打乱
（数值比较通过但显示错误），因此补了格式化器自检
`Hex64(0x0123456789ABCDEF) == "0123456789abcdef"`，并把"期望/实际"改为两块独立缓冲区，
避免共用静态缓冲导致两值打印成同一个。

### 3.5 CMake 侧的选择
- `CXX_EXTENSIONS OFF` + MSVC `/permissive- /utf-8 /Zc:__cplusplus /Zc:preprocessor /W4`；
  非 MSVC 分支用 `-Wall -Wextra -Wpedantic`，为将来 clang/GCC 交叉验证留口。
- 严格选项集中在 `epocanva_strict` INTERFACE 目标，后续任何目标 `target_link_libraries` 即继承，
  避免每个 CMakeLists 复制一份编译开关。
- **不使用 FetchContent / ExternalProject 联网**；`third_party/` 只有规则文档。
- 预设用 `Visual Studio 17 2022` + `architecture: x64`，
  **不写 toolset 版本号、不写编译器绝对路径**；因 Ninja 未安装而**不提供** Ninja 预设。
- 多配置生成器下测试预设显式带 `configuration: Debug/Release`，
  否则 CTest 定位不到 `$<TARGET_FILE:...>` 解析出的可执行文件。
- `tests/infrastructure` 在缺少探针目标时直接 `FATAL_ERROR`，
  而不是静默跳过——静默跳过会让"0 个测试通过"看起来像成功。

### 3.6 文档层面的几个刻意取舍
- `overview.md` 通篇以"规划"口吻书写，并带**实现状态表**把每个模块标为未实现，
  避免文档被后续读者误当作现状。
- ADR 0003 与威胁模型 3.8 明确写出：
  **Windows 普通 TSF DLL 得不到 OS 级网络阻断**，该处保证是架构/工程性的；
  Android 侧才是平台强制（靠不申请 `INTERNET`）。两处措辞分开，不合并成一句"绝不联网"。
- 威胁模型第 1 节把"EpoCanva 自身外传"与"目标应用发送已上屏文字"分成 A/B 两类，
  并明文禁止"用了本产品就拿不到你的密码"这类虚假宣传；
  第 3.4 节给出删除语义的允许措辞，禁用"不可恢复/彻底粉碎/永不泄露"。
- 全部文档不含许可证声明（README 明确写"尚未确定"）。
- AGENTS.md 覆盖：英文优先且禁止 ASCII 直通/单 Translator、禁止伪造结果、
  禁止越阶段、隐私与离线、偏移必须带单位、先核对真实源码、禁止就地改第三方、
  禁止自动 commit/push、构建产物只落 `build/`。

### 9.3 构建配置的决定与理由

1. **`cmake_minimum_required(VERSION 3.25)` 保持不变**，预设 schema 保持 **version 6**，
   目的是让同一份预设能被 3.25 一直到 4.x 读取；本轮**没有**引入任何更高版本特性。
2. 主路径预设 `vs2026-x64-debug` 按任务书保留（generator `Visual Studio 18 2026` + `architecture: x64`
   + 同名 build/test 预设 `configuration: Debug`）。它在本机 exit 1，失败原文记录在 9.5。
   任务书写明该路径需 CMake ≥ 4.2；本机最高 3.31.6 且不联网，
   所以"4.2"在本报告里是**上游给出的、待复验的**门槛，不是我验证过的数字。
3. `vs2022-x64-debug` 作为当前唯一可实跑的验收路径加入：同样的 x64 + MSBuild + Debug 形态，
   区别只在 VS 生成器版本号。
4. **构建目录天然隔离**：`binaryDir = build/${presetName}` →
   `build/vs2026-x64-debug`、`build/vs2022-x64-debug`、`build/manual-cl` 互不干扰；
   失败的 vs2026 配置**没有**留下缓存目录，也没有在旧缓存上换生成器。
5. 共享预设里**不含本机绝对路径、不含 `-T` 工具集版本号**（用默认工具集，实测由 CMake
   自行选中 Professional）。需要锁实例时改用被 Git 忽略的 `CMakeUserPresets.json`，理由写进 bootstrap 第 3 节。
6. **test 预设不能自动构建**：CMake 自带手册 `cmake-presets(7)` 的 test preset 字段表里没有
   `buildPresets`，第一轮写的该字段被 CMake 拒绝：
   `Invalid extra field "buildPresets" in Preset`（exit 1）。已删除，流程明确为 configure → build → test。
7. **开关传播已用真实构建日志核实，不再依赖"INTERFACE 目标会自动传播"的假设**：
   `--verbose` 重建后的实际 cl 命令行含
   `/std:c++17 /permissive- /utf-8 /Zc:__cplusplus /Zc:preprocessor /W4 /EHsc /Gw`
   以及 `-D_CRT_SECURE_NO_WARNINGS -DNOMINMAX -DWIN32_LEAN_AND_MEAN`。
   同时必须如实说明：`CMAKE_CXX_EXTENSIONS OFF` 对 MSVC **不产生可见开关**
   （MSVC 无 GNU 扩展模式），MSVC 侧的严格性实际来自 `/std:c++17` + `/permissive-`；
   CMake Debug 默认 `/MDd`（动态调试 CRT）也在这条命令行里得到确认。

### 9.4 CTest 判定改造

第一轮用 `PASS_REGULAR_EXPRESSION` + `WILL_FAIL` 组合，二者都是间接判断，
且各自可能"因为错误的原因通过"。本轮统一为显式退出码核验：

- 包装脚本 `tests/infrastructure/assert_probe.cmake` 用 `execute_process` 调探针，
  分别捕获 `RESULT_VARIABLE` / `OUTPUT_VARIABLE` / `ERROR_VARIABLE`；
- 先要求结果必须是**数字**退出码（非数字 = 启动失败、超时或被终止 → 直接 FATAL_ERROR）；
- 再与 `-DEXPECTED_EXIT` 做**精确整数相等**比较；
- 再用 `string(FIND)` 做**字面**标记检索（不用正则），
  正向用例要求 `RESULT PASS` 必须出现（防止"提前 return 0"冒充通过），
  负向用例要求它必须不出现；另加一条与调用参数无关的不变式：
  非零退出码 + 出现成功标记 = 自相矛盾，一律失败；
- 全程不做 shell 拼接，探针路径与每个参数都是 `execute_process` 的独立列表项，
  含空格的路径原样可用（实测 argv 显示 `D:/Users/Smart Kevin/.../epocanva_toolchain_probe.exe` 为单个元素）；
- 超时双层：包装脚本 `TIMEOUT 30`（`execute_process`），CTest `TIMEOUT 60`，
  保证挂死时由包装脚本给出可解释的失败原因；
- 参数传递用 `PROBE_ARG1` / `PROBE_ARG2` 两个显式槽位，而不是 `;` 列表——
  因为若分隔符被吃掉，列表写法下"两个参数"会退化成"一个奇怪参数"，
  探针仍然返回 5，测试会**因为错误的原因通过**；用显式槽位时丢第二个参数会让探针返回 0，与期望 5 不符而暴露。

四个用例与探针实际行为（`main.cc` 的 `ExitCode` 枚举与 `main()` 分支核对一致）：

| 用例 | 参数 | 期望退出码 | 期望 `RESULT PASS` | 源码依据 |
| --- | --- | --- | --- | --- |
| `infrastructure.toolchain_probe.selftest` | `selftest` | 0 | 必须有 | `main()` 走完四项检查后打印 `RESULT PASS` 并返回 `kOk=0` |
| `infrastructure.toolchain_probe.forcefail` | `forcefail` | 9 | 必须无 | `kForcedFailure=9` 分支，只打印 `FAIL ...` |
| `infrastructure.toolchain_probe.unknown_mode` | `not-a-real-mode` | 5 | 必须无 | 落到 usage 分支 `kUsage=5` |
| `infrastructure.toolchain_probe.extra_args` | `selftest extra` | 5 | 必须无 | `argc > 2` 先返回 `kUsage=5` |

约定一致性核对结果：**源码与本节表格完全一致，没有为了通过测试而调整退出码**。
唯一与第一轮文档不一致之处是"参数过多"这条路径此前只在手工记录里出现过，
现在正式成为第 4 条用例。

### 9.7 撤回的表述

第一轮及以下文档中出现过"用导入表/依赖列表支撑离线承诺"的写法，本轮**明确撤回**：
