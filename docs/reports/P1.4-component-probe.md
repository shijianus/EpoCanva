## 2. 决定接入方式前核实的事实（全部读自固定提交）

| 事实 | 【源码】 |
| --- | --- |
| 上游合并插件的唯一入口是 `add_subdirectory(${plugin})`，名字来自 `ENV{RIME_PLUGINS}` 或 glob | `third_party/librime/plugins/CMakeLists.txt:24-47` |
| 环境变量分支先把 `[^ ]*/` 前缀剥掉，再把**空格变成分号** | 同上 `:29-30` |
| 官方样例对上游做法的表述就是"link or copy the directory to `plugins/`" | `sample/CMakeLists.txt:36` |
| 插件 objects 进 `rime` 目标靠 `$<TARGET_OBJECTS:…>` 汇入 `rime_plugins_objs` | `plugins/CMakeLists.txt:20` → `src/CMakeLists.txt:29-35, 84` |
| `RIME_SETUP_EXTRA_MODULES`（即 `kDefaultModules` 的扩展）只能来自上面那个插件目录的 `plugin_modules` | `CMakeLists.txt:264-271`、`src/CMakeLists.txt:174-177`、`src/rime/setup.cc:25` |
| `ENABLE_EXTERNAL_PLUGINS=ON` 唯一能给的模块名是 `plugins`，而它 `initialize()` 会用 Boost.DLL 遍历 `rime-plugins/*.dll` 逐个装载 | `plugins/CMakeLists.txt:12-22`、`plugins/plugins_module.cc:35-70, 122-125` |
| **`RimeTraits.modules` 是公开 C API 的模块装载入口**：给了就用它，没给才用 `kDefaultModules` | `src/rime_api.h:101`、`src/rime_api_impl.h:51-54`（`RimeInitialize`）、`:109-110`（`RimeDeployerInitialize`） |
| 模块自注册是库装载期的 `.CRT$XCU` 静态初始化 | `src/rime_api.h:528-533, 557-571`、`src/rime/module.cc:13-15` |
| 自定义 API 走模块的 `get_api` 槽，是上游自己的用法（levers） | `src/rime/lever/levers_module.cc:35-40`、`levers_api_impl.h:242-280` |
| `Component<T>::Create` = `new T(arg)`；引擎用 `an<>` 持有并负责销毁 | `src/rime/component.h:34-38`、`src/rime/engine.cc:298-327` |
| 未注册的组件名被跳过而不是中止：`Require` 返回空 → `LOG(ERROR)` + `continue` | `src/rime/engine.cc:310-315` |
| 处理器链按列表顺序，第一个 `kAccepted` 胜出并 `return true` | `src/rime/engine.cc:99-104` |
| `Switcher` 恒为 `processors_[0]`，配置顺序在其后 | `src/rime/engine.cc:337, 350` |
| **测试键**：`XK_F6 = 0xffc3`；`0xffbe` 是 `XK_F1` | `include/X11/keysymdef.h:257`、`:252` |
| 修饰位：Shift=1<<0，Control=1<<2，Release=1<<30 | `src/rime/key_table.h:13-43` |
| `RimeFinalize` 会 `Registry::Clear()`（删除 Component 对象）+ `UnloadModules()` | `src/rime_api_impl.h:58-63`、`src/rime/registry.cc:31-37` |

**结论**：上游**没有**接受树外源码路径的现成入口。任务书第二/三节的组合约束
（同一 PE 模块、不建独立插件 DLL、上游工作树不被改写）因此指向
**最小项目侧 CMake 适配**，而不是继续等待选型。

## 3. 实际采用的接入方式

1. `-DCMAKE_PROJECT_rime_INCLUDE=tools/cmake/epocanva_rime_compiled_in_components.cmake`。
   CMake 官方把该变量描述为"用于把自定义代码注入项目构建而**不修改其源码**"，
   并且本仓库在 P1.2 已用同名机制（`CMAKE_PROJECT_opencc_INCLUDE`）解决过 OpenCC。
2. 钩子在 `project(rime)` 之后立刻执行：此时 `rime` 目标还不存在，
   于是 `add_subdirectory(engine/rime_components/probe …)` 先建 OBJECT 库，
   再用 **`cmake_language(DEFER CALL …)`** 把 attach 排到**当前目录处理结束**时执行
   （本机 CMake 3.31.6 的帮助文本原文："executed as if written at the end of the
   current directory's `CMakeLists.txt` file"）——即在 `add_subdirectory(src)` 之后。
   attach 内容为 `target_sources(rime PRIVATE $<TARGET_OBJECTS:epocanva_rime_probe_objs>)`，
   与上游自己传 objects 的写法同构。
3. **自有模块名不写进 `kDefaultModules`**（那需要上游插件目录机制）。
   前端在公开 C API 的 `RimeTraits.modules` 里列出 `"epocanva_probe"`，
   由 `RimeInitialize → LoadModules(traits->modules)` 装载。
   代价与"忘记列名会静默不装载"这一后果写入 ADR-0004「限制」第 2 条，
   并由本轮的行为学断言承担检验责任。
4. 诊断通过模块的 `get_api()` 返回 `EpoCanvaProbeApi`（`int data_size` + 三个函数指针）：
   `get_counters(调用方分配的定长结构)`、`reset_counters_when_idle()`、`build_id()`。
   **没有新增任何导出符号**（§5 的导出表比对证明）。

## 4. 命令（真实执行序列）

```powershell
# 1. 自有组件引擎（不重建依赖、不下载）
tools/build_librime_baseline.ps1 -Mode component-probe -Fresh -Verbose_Build
#   -> exit 0；9 个编号步骤；日志 build/librime-component-probe/logs/01..09-*.log

# 2. 可达性测试工程（两个可执行文件 + 5 条 CTest）
cmake -S tools/rime_component_probe -B build/librime-component-probe/probe `
      -G "Visual Studio 17 2022" -A x64 -DCMAKE_CONFIGURATION_TYPES:STRING=Release `
      -DRime_Install_Prefix:PATH=<repo>/build/librime-component-probe/rime/install `
      -DBaseline_Rime_Prefix:PATH=<repo>/build/librime-baseline/rime/install `
      -DEpoCanva_Rime_Input_Replay_Exe:FILEPATH=<repo>/build/librime-baseline/replay/Release/rime_input_replay.exe
cmake --build build/librime-component-probe/probe --config Release      # exit 0
ctest --test-dir build/librime-component-probe/probe -C Release --output-on-failure --no-tests=error   # exit 0

# 3. 原有回归（三条命令，各自 exit 0）
ctest --test-dir build/librime-baseline/replay  -C Release ...
ctest --test-dir build/librime-baseline/smoke   -C Release ...
ctest --test-dir build/vs2022-x64-debug         -C Debug   ...
```

所有命令都在 VS2022 Professional 的开发者环境里执行（`Enter-VsDevShell`），
cmake/ctest 用该实例自带的 3.31.6-msvc6。完整 stdout 与逐步参数落在
`build/librime-component-probe/logs/`（git 忽略）。

最后把 4 个测试目录串起来跑了一遍汇总回归（新增 5 + 原有 7），

## 6. 组件与诊断的实际语义

| 计数 | 何时 +1 | 断言用途 |
| --- | --- | --- |
| `module_initialized` / `module_finalized` | 模块 `initialize()` / `finalize()` 被 `ModuleManager` 调用 | 证明装载走 librime 机制，而非静态初始化副作用 |
| `component_constructed` / `component_destroyed` | 构造函数 / 析构函数 | 引擎真的建了组件；会话销毁真的释放了 |
| `live_instances` | 构造 +1，析构 −1（直接维护，不是差值推算） | 泄漏判据：轮初/轮末相等，全清后为 0 |
| `process_key_calls` | 每次 `ProcessKeyEvent` 进入 | 键确实到达自有组件 |
| `keys_passed_through` | 返回 `kNoop` | 字母被放行（保持原链路） |
| `test_keys_consumed` | 裸 F6（`keycode()==0xffc3 && modifier()==0`）返回 `kAccepted` | 消费确实由该组件做出 |

存储是 `std::atomic<unsigned long long>`（relaxed），组件**不含一条 LOG**，
不读取任何配置，不调用任何 `Context` 方法。
所有权：计数写入调用方自分配的定长结构；`get_api()`/`build_id()` 返回 DLL 内静态存储，
调用方不释放；`reset_counters_when_idle()` 在有活实例时**返回 False 且不改任何计数**
（这条本身被断言）。`finalize()` 之后程序**不再触碰**该接口。

## 9. 未解决问题与风险

1. **英文能力仍为零**。本轮组件只做计数与一个测试键的消费；候选文本与按键逐字节相同。
   **禁止**把 P1.4 描述为英文补全、预测、纠错、分词或"英文 MVP 的一部分"。
2. **自有模块不在 `kDefaultModules`**。任何前端（未来的 TSF DLL、Android JNI 侧、
   命令行工具）若忘了在 `RimeTraits.modules` 里列出 `epocanva_probe`，
   组件会**静默不装载**（`src/rime/setup.cc:33-40` 对找不到的名字直接跳过）。
   因此**每个自有组件都必须配一条行为学断言**，且这一约束要进适配层的验收。
   若产品要求"第三方复用引擎 DLL 时零配置"，需要一条最小上游补丁
   （把模块名并入 `plugins/CMakeLists.txt` 的 `plugin_modules` 通道，
   或让 `add_subdirectory` 接受树外源码目录）——按 `AGENTS.md` §7 走补丁流程，
   **本轮没有打，也没有擅自改用独立插件 DLL 绕过**。
3. **接入依赖 `cmake_language(DEFER …)`**（CMake ≥ 3.19；本机 3.31.6）。
   降级 CMake 会使 component-probe 模式在 configure 阶段直接失败——
   失败是显式的，不会静默产出"没有组件的组件版"。
4. **`.CRT$XCU` 静态初始化在 `/O2 + /OPT:REF /OPT:ICF` 下的存活**是本轮实测得到的
   （`module.before_setup registered by DLL load`）。
   如果将来改成 LTCG、或把组件挪进静态库再链入，"objects 被链接器裁剪"的风险会重新出现；
   那时 §5.2 第 1 项与 §5.4 前两条必须重跑，不能靠源码推断。
5. **`--mode` 与 DLL 必须配对**这一运维约束由 `--expect-dll` + 运行时反查模块保证；
   但 CI 化时若把两个 exe 拷进同一目录，`rime.dll` 只可能留一个。
   运行目录布局要按 `component-engine/`、`baseline-engine/` 原样保留。
6. **`/MT=8` 的含义**：MSBuild 的 verbose 输出把整批源文件合并打印成 8 条 cl 命令行，
   不是"只编了 8 个文件"（objects 计数 115、CRT ABI 标签逐 obj 核对可反证）。
   脚本沿用 P1.2 的"`/MT` 计数 > 0 且 `/MD` 计数 == 0"判据，但**这一条对
   "命令行抽样"的依赖弱于对 obj ABI 标签的依赖**；后续如要更强判据，
   应改为对 `rime.vcxproj` 的 `PreprocessorDefinitions`/`RuntimeLibrary` 逐项断言。
7. **默认模式的完全绿色认证需要 `-Mode baseline -Fresh -Verbose_Build` 全量重建**
   （含四个依赖），本轮按要求**没有重跑**（见 §8 末段）。
   baseline 的认证状态仍应引用 P1.2 报告，P1.4 只提供"未被混入"的等价判据。
8. **依赖复用带来的顺序耦合**：component-probe 模式必须先有一次成功的
   `-Mode baseline`。干净机器上的顺序是 baseline → component-probe，
   脚本对此给出的是显式 throw 而不是回落到系统库。
9. **词库许可审查仍未完成，`build/` 整棵树禁止对外发布**（沿用 P1.2/P1.3）。
   本轮日志再次实测到上游复制了 **7** 个 `data/minimal` 文件进构建树。
   测试夹具完全来自 `tests/fixtures/`，未使用这些文件。
10. **运行包装脚本仍未纳入版本管理**：本轮用的 configure/build/test 包装件在
    `build/`（git 忽略，未审计）里：`p14-scratch-probe.ps1`、`p14-scratch-tool.ps1`、
    `p14-syntax-check.ps1`。命令本身已在 testing 文档逐条给出。
    是否升级为 `tools/` 下的正式入口，需要负责人决定（P1.3 §9 第 6 项同一问题）。
11. **未覆盖路径**（明确列为缺失，不算通过）：`select_candidate`、`change_page`、
    `get_schema_list`、`simulates_key_sequence`、`start_maintenance` 线程路径、
    有词典 schema 的部署、多候选与翻页、非 ASCII 输入与 UTF-8/UTF-16/字素簇换算
    （`AGENTS.md` §5 要求在写平台适配层之前定义，仍未定义）。
12. **探针组件本身不是产品能力**，不能进入发行物。它是接入通路的见证件；
    第一个真实组件（英文候选/形态变化）在下一阶段的验收里**不得**沿用"计数与一个 F6"
    作为通过判据。
13. **DLL 的 SHA-256 不能当可复现性校验用**（§5.5 实测：同一份源码重链一次，
    只差 28 个链接时刻/GUID 字节）。任何"哈希相同才算构建成功"的 CI 判据在这里都会
    假失败；正确的判据是与时刻无关的那一组（obj 计数、字符串命中、导出表差集、
    运行时诊断计数）。若将来需要字节级可复现，要先向上游提补丁固定
    `/LINKER:...` 的时间戳来源（例如 `SOURCE_DATE_EPOCH`），那属于 `AGENTS.md` §7
    的补丁流程，**本轮没有做**。
14. **复现轮没有重跑 `-Mode baseline` 的全量构建**（任务书要求不重建依赖）。
    因此 baseline 的"完全绿色认证"仍以 P1.2 报告为准；本轮只以 §8 的等价判据
    证明默认模式产物未被自有组件混入，并确认其 `rime.dll`/`rime.lib` 哈希未变。
