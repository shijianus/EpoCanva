## 2. 本轮实际做了什么（一句话契约）

同一个词根 `hel` 的三种大小写形态，得到三套互不相同、但都排在原文之后的候选：

```
hel  ->  hel | hello | help | helmet          （小写形态：候选保持词表原样）
Hel  ->  Hel | Hello | Help | Helmet          （首字母大写：候选首字母大写）
HEL  ->  HEL | HELLO | HELP | HELMET          （全大写：候选全大写）
HeL  ->  HeL                                   （混合：不补全，只有原文）
```

而**默认提交永远是用户自己打的那串**：`Hel` 直接回车提交 `"Hel"`，
只有在候选菜单里明确选中第 1 项，才提交 `"Hello"`。

## 3. 关键设计决定与被否决的替代方案

| 决定 | 理由 | 被否决的方案 |
| --- | --- | --- |
| 分类放在核心层，Translator 只按分类结果分桶 | 核心层可单测、无 Rime 依赖；Translator 不重复实现规则 | 在 Translator 里直接 `std::transform(tolower)`——不可单测，且会依赖 locale |
| 四段文本严格分离：raw / lookup key / canonical / display | 任务书第五节点名要求；也是 preedit 不被污染的前提 | 原地小写化 `input`——会让 preedit 与用户按键不一致，提交文本无法解释 |
| 单个大写字母 `H` 判为 `initial_capital`（优先级 3 在 5 之前） | `H→Hello` 是任务书给的用例；若先跑"全大写"规则就会得 `HELLO` | 把单字母并进 uppercase；或拒绝单字母查询 |
| `mixed` 只出原文，且计入 `queries_mixed_case` 而**不是** `lexicon_load_failures` | 任务书第七节：混合大小写不能记成词表加载错误；两者产品含义不同 | 猜测一个形态（`HeL`→`Hello`）——用户无法解释被改写的按键 |
| 词表仍只存小写，display 在查询时现算 | 不复制索引、不重建缓存；`HEL` 与 `hel` 命中同一段区间 | 为每种大小写建一份索引——内存翻倍且没有新信息 |
| **去重在 k 截断之前** | 先截断再丢弃会让重复项吃掉一个名额，返回少于预算的候选 | 先截断后去重（P2.1 的形状）——候选数会随大小写不稳定 |
| 非 ASCII 字节 → `kNotAlphabetic`，与 `kMixed` 分开 | 只有 52 个 ASCII 字母参与映射；这不是通用折叠 | 引入 `towlower`/`std::locale`——本轮明确不做，见 §11 |
| 诊断结构**尾部追加**字段 | `data_size` 版本守卫让旧调用方失败而非误读 | 复用旧字段名重定义语义——会让历史日志与本轮日志不可比 |

## 4. 决定接入方式前核实的事实（全部读自固定提交 `33e7814`）

1. **【源码】** `Speller::ProcessKeyEvent()`（`src/rime/gear/speller.cc:100-130`）：
   可打印键必须在 `speller/alphabet`（或 delimiter）里才会进入组合，否则**被丢弃**；
   它使用 `key_event.keycode()` 原值（:104），对 `shift()` 的唯一引用是空格键（:107），
   丢弃不在集合里的键在 :109-110。
   ⇒ 大写能进组合区，**只能**靠大写 keysym，这也是 schema 扩 alphabet 的直接依据。
2. **【源码】** `KeyBindingProcessor` 在匹配按键绑定时会剥掉 `kShiftMask`
   （`src/rime/gear/key_binding_processor_impl.h:31,38`，两处 `& ~kShiftMask`）。
   ⇒ `shift + 'h'` 走的是绑定表路径，不会把 `H` 送进 speller。
   **这条不是推断**：本轮实测 `shift+h` 之后 `preedit="h"`（§7.6）。
3. **【源码】** `AbcSegmentor::Proceed()`（`src/rime/gear/abc_segmentor.cc:39-69`）逐字节
   用 `alphabet_.find(input[k])` 判断是否继续切分（:46），并在 :50-54 检查 initial；
   `speller/initials` 未配置时 `initials_ = alphabet_`（`speller.cc:95-97`）。
   ⇒ alphabet 里 `a` 与 `A` 是两个不同字符，混合大小写串（`HeL`）仍会被整段切出来送进
   Translator——这一点由 §7.4 的 `HeL` 实测行证明，不是从代码推出来的。
4. **【源码】** `ConcreteEngine::TranslateSegments()`（`src/rime/engine.cc:203-231`）把
   `segments->input().substr(segment.start, len)` 原样交给 Translator，**不在这条路径上做任何大小写处理**。
5. **【源码】** 本 schema 只列 1 个 translator，因此 `Menu` 只聚合 1 个 translation，
   `FifoTranslation` 的**追加顺序即候选顺序**（`menu.cc:15-22` → `translation.cc:127-152`）。
   ⇒ 原文在 0 号位由 `Query()` 保证，不需要 `echo_translator`。
6. **【源码】** `Composition::GetCommitText()` 用 `cand->text()` 组装提交文本；
   未 select 时提交的是原始组合串本身 ⇒ "默认提交原文"不是本轮代码的性质，而是引擎的既有行为，
   本轮只是**没有破坏它**（实测见 §7.2、§7.4）。
7. **【源码】** `src/rime/key_table.h:14-45` 定义修饰位；`include/X11/keysymdef.h:568,601`
   定义 `XK_H = 0x0048` / `XK_h = 0x0068`。本轮所有大写键值取这里的字面常量，未凭记忆书写。
8. **【实测】** `process_key()` 对本轮的每个大写键都返回 `handled=1`，且没有任何一步由测试程序
   直接写 `context`——大写全部经 `RimeApi::process_key()` 注入。

## 5. 契约与单位

- `CaseStyle` 7 值：`empty / lowercase / initial-capital / uppercase / mixed-case / not-alphabetic / input-too-long`。
- 分类优先级（`english_case.h:58-71` 与实现一致）：空 → 超长(>64B，**不截断**) → 含非字母字节 →
  单字母 → 全大写 → 首字母大写+余下小写 → 全小写 → 其余全字母组合判 `mixed`。
- 单位：输入/词长上限 `64` **UTF-8 码元**（本轮实际输入全 ASCII，等于字节）；
  `preedit` 长度＝码元数；候选序号＝0 基菜单位置；`k`＝候选条数（**不是**字节偏移）。
- 候选预算不变：原文 1 条 + 补全 ≤ 7 条 = ≤ 8 条（`page_size: 8`）。
- 大小写映射只对 52 个 ASCII 字母生效；`display` 是**提交文本**，`canonical` 只在核心内部用于排序与去重。
- 排序契约不变：weight 降序 → canonical 升序（按字节），与大小写无关，
  因此同一查询换一种大小写不改变名次（核心第 19 组断言）。

## 6. 诊断面：五种"没有补全"仍然可区分

`counters.final`（§7 同一次运行）里：

```
attempts=1 ok=1 fail=0 entries=49 errline=0        # 词表：一次成功加载，无失败
queries=33 with_index=33 orig=33                   # 每次都带索引查询，0 号位都是原文
rejected=1 mixed=1 notalpha=0 toolong=0 nomatch=1  # 四种"没有补全"分开计
compl=172 cl=36 ci=97 cu=39                        # 三种形态各自的候选数
```

（逐字取自 `counters.final` 那一行，字段顺序与程序输出一致：
`mod_init=1 mod_fin=0 xl_ctor=4 xl_dstr=4 xl_live=0 attempts=1 ok=1 fail=0 entries=49
errline=0 queries=33 with_index=33 rejected=1 orig=33 compl=172 no_path=0 nomatch=1
mixed=1 notalpha=0 toolong=0 cl=36 ci=97 cu=39`。）

不变式（集成测试直接断言，不是事后解释）：
`rejected == mixed + notalpha + toolong`、`compl == cl + ci + cu`、
`with_index == queries`（本模式没有空输入查询）、`attempts` 恒为 1。

`mixed` 与 `fail` 是**两个计数器**，因此"混合大小写只出原文"永远不会被读成"词表坏了"。

## 7. 真实结果（全部摘自 `build/p22-verify/evidence-case-preservation.log`）

运行程序 `rime_english_completion.exe --mode case-preservation`，退出码 **0**，

ev=12 Return                                   commit="HEL"
ev=32 Return after select (HEL)                commit="HELLO"
```

### 7.4 单个 `H` 与 `HeL`、`Hello`

```
ev=13 'H'    preedit="H"[len=1]  cands=8 list=H|Hello|Help|Hen|Hel|Helmet|He|Herb
ev=14 Return                                   commit="H"            # 单字母按首字母大写处理

ev=23 'Hello' preedit="Hello"[len=5] cands=1 list=Hello             # 去重：原文已在 0 号位

```
ev=36 BackSpace from HEL  preedit="HE"[len=2] cands=7 list=HE|HELLO|HELP|HEN|HEL|HELMET|HERB
```

### 7.5 Session 交替（防串话）

同一进程、两个 session，A 保持 `HE`、B 保持 `he`，交错查询：

```
ev=39 'HE on A'  preedit="HE"[len=2] cands=7 list=HE|HELLO|HELP|HEN|HEL|HELMET|HERB
ev=41 'he on B'  preedit="he"[len=2] cands=7 list=he|hello|help|hen|hel|helmet|herb
```

两个 session 的 preedit 与候选形态互不污染；`attempts` 仍为 1，
`translator_constructed=4`、`translator_destroyed=4`、`live=0`（释放干净）。

### 7.6 大写到底是怎么进来的（记录实际采用方式，不伪造状态）

```
ev=44 shift+h  preedit="h"[len=1] cands=8 list=h|hello|help|hen|hel|helmet|he|herb
```

**实测结论**：`mask=kShiftMask + keycode=XK_h` 被 `KeyBindingProcessor` 剥掉 shift 后按小写处理，
只得到 `h`；因此本轮所有大写输入一律送**大写 keysym**（`XK_H = 0x0048` 等），
这也是 §4.2 那条源码事实的可执行验证。测试程序没有用写 context 的方式伪造大写。

## 10. 未完成项与风险

1. **词表仍是 49 行手写夹具**，不是词典；`Hel` 只能补出这 49 行里的词。
2. **只有 ASCII 52 字母**。带重音、德语ß、土耳其语 i 之类输入直接判 `not-alphabetic`，
    行为是"不补全、保原文"，不是错误，但也不是能力（见 §11）。
3. **混合大小写一律不补全**。产品上"iPhone"这类会被判 mixed；本轮按任务书不猜。
4. **句首自动大写、专名/品牌大小写恢复、学习**均未实现。
5. 缓存无热重载：改词表需要重建/重跑，本轮明确不做（任务书第九节）。
6. 候选预览未做：preedit 仍是原始组合串（任务书第六节要求本轮保持）。
7. `english_case` 的 display 是**逐字节重打**，若将来词表允许非 ASCII，`ApplyCaseStyle`
   必须整体重写而不是打补丁——这一点写在头文件注释里，但实现仍是 ASCII-only。
8. english 模式的 hook label 文案仍是 `P2.1`。它是模式标识、不是阶段声明，
   但会让不熟悉的人误读构建日志；改它要重新登记已哈希的构建入口，本轮按任务书第九节
   "够用就复用"没有动。
9. 风险：`speller/alphabet` 加入大写后，理论上任何依赖"alphabet 只含小写"的上游行为都会变。
   本轮核对了 speller / abc_segmentor / key_binder 三处，且 P1.4 探针 5/5、P1.3 回放 2/2、
   P1.2 smoke 1/1 都在各自引擎上复跑通过；**但这三处不是穷举**。
