## 3. 关键设计决定与被否决的替代方案

| 决定 | 理由 | 被否决的方案 |
| --- | --- | --- |
| 词形、大小写、索引结果**三个独立答案**（`TokenAnalysis` / `CaseStyle` / `CompletionOutcome`） | 任务书第三节明确不许用一个 bool 混淆状态；四者产品含义不同 | 一个 `bool is_protected` 或把一切折叠成 `no-match` |
| 结构判定**先于**大小写判定，且**先长度后内容** | 65 字节里第 70 个字节是数字时，正确说法是"超长"，不是"受保护"；用前 64 字节分类等于偷偷截断 | 先截断再分类；或先分类内容再看长度 |
| 词表校验与查询层调用**同一个** `IsDictionaryEntryForm` | "能加载的词必须能查到"。两处各写一遍语法必然漂移，症状是词表加载干净却永远补不出来 | 加载器和查询器各写一套字母表 |
| 区间上界改用**前缀后继** `key[0..n-2]+(key[n-1]+1)` | P2.1 的 `key+'{'` 依赖"后续字节全 ≤ `z`"，那是**词表的性质**不是算法的性质；词表一含 `'`(0x27)/`-`(0x2D) 就变成运气。后继式的正确性证明里不出现 `z`、`{` 或词表字母表 | 保留 `+'{'` 并"验证一下当前词表还能用" |
| 技术性文本的保护放在**alphabet + 核心层**，不加新组件 | 见 §4.1–4.3：不在 alphabet 的键会被 speller **丢掉**，组合停在 `user`；剩下 `@example.com` 会被 `fallback_segmentor` 切成 1 字节 raw 段，于是自有 Translator 收到的是字母段 `user` —— 那才是任务书说的"仅扩展 alphabet 但让 segmentor 继续拆出尾部，不算完成保护" | 写一个自有 Processor 去拦键；或只做核心层判定然后假装引擎不会切段 |
| 停止原因报**类别 + 码元偏移**，不报字节值 | `@` 与 `2` 的区别足够诊断用；把用户按键的值搬进对外表面没有收益 | 直接回传 stop byte |
| `initial_capital` 只大写整词第 0 个字母 | 任务书第三节：标点位置不改变、不把连字符后自动大写，所以 `co-operate → Co-operate`，而输入 `Co-Operate` 判 mixed 保留原文 | 词首大写（title case）——那是另一种语言产品决定，本轮不做 |
| 保护是**每帧**性质，不是闩锁 | 实测：`hel` 4 项 → 键入 `@` 塌成 1 项 → 退格后 4 项恢复。计数按"从停止字节起每帧 +1"断言，等式是 `帧数 = 串长 − 停止偏移` | 只在最后一个帧上断言（会漏掉"中途已经把尾部补全发出去"的情况） |

## 5. 契约（含单位）

- `QueryDecision` 7 值：`query / empty / input-too-long / non-ascii / protected-text / unsupported-byte / illegal-form`。
- `DelimiterForm` 6 值：`no / internal / trailing / leading / more-than-one / both-kinds`。
  `internal`、`trailing` 是仅有的两种可查询状态；`leading`、`more-than-one`、`both-kinds` 一律 `illegal-form`。
- `CompletionOutcome` 9 值：`completed / no-match / empty-input / input-too-long / non-ascii / protected-text / unsupported-byte / illegal-word-form / mixed-case`。
  `no-match`（查了没中）与 `protected-text`（不该查）**不是一个东西**。
- 长度上限 64 **UTF-8 码元**（本轮字符全 ASCII ⇒ 等于字节），三处别名同一个常量：
  `kMaxCaseInputBytes = kMaxTokenBytes = kMaxWordBytes = kMaxPrefixBytes`。
- `stop_offset`、`delimiter_offset`＝码元下标；`PrefixRangeStart/End` 返回的是**条目下标**（半开区间）；
  `preedit_length`＝码元；候选序号＝0 基菜单位。
- 排序不变：weight 降序 → 规范词**字节**升序；`'`(0x27) 与 `-`(0x2D) 都小于 `a`(0x61)，
  所以 `co-operate < coopt`、`don't < done` —— 这正是区间边界测试要卡的地方。
- 预算不变：原文 1 + 至多 7 补全 = 至多 8；去重在截断**之前**、在显示文本上；默认提交仍是原文。

`api.balance status 470/470 context 470/470 commit 470/470 -- paired`；
`attempts` 全程 1；日志目录保持为空。

**真实链路到不了的两个桶（据实说明，不记作通过）**：
`queries_non_ascii` 与 `queries_unsupported_byte` 在引擎运行里恒为 0——
非 ASCII 字节和空格/`;`/`"` 这类字节**不在** `speller/alphabet` 内，
speller 直接丢弃（§4.1），组合里根本不会出现它们，所以 Translator 收不到。
它们在核心层被完整覆盖（用例组 22 逐条断言 `non-ascii` / `unsupported-byte`）。
换句话说：非 ASCII 输入目前在产品上表现为"字符进不了组合区"，
这是本轮**已知限制**而不是被掩盖的失败（§10 第 2 条）。

## 8. 本轮修掉的缺陷

### 8.1 第一次引擎构建 exit 1（我自己的代码编译不过）

我自己写的 `completion.display.find(...)` 字符常量漏了转义，成了空字符常量，

`english_token.obj MT_Static=1 MD_Dynamic=0`（`build/p23-verify/engine-english-fresh.log`）。

### 8.2 P2.2 的三处期望值在 P2.3 必须改，改的是期望不是断言强度

`hel-lo`、`n't`、`a-b`、`a'b` 在 P2.2 是 `not-alphabetic`；P2.2 的字母表里没有分隔符。
本轮把它们从"被拒绝"表移到"能查询"表，并加了两条新的、更强的断言：
分隔符词形合法但词表没有该行时必须报 `no-match` 且 `lookup_performed == true`
（"词表里没有"与"这类输入不该查"从此可分）。`ExpectLoad("a-b\t5\n", illegal-word)`
同样改为 `kOk`，并补齐 12 行词形/字节的分别断言（用例组 21）。

### 8.3 集成测试期望算错，被自己的断言抓住（15 条失败，0 条引擎缺陷）

| 失败断言 | 我的错 | 正确推导（已由引擎实测确认） |

## 10. 未完成项与明确限制

1. **词表仍是 54 行手写夹具**，不是词典；`don'` 只能补出这 54 行里的词。
2. **非 ASCII 与空格类字符进不了组合区**（不在 `speller/alphabet`），
   因此 `queries_non_ascii` / `queries_unsupported_byte` 只在核心层可达（§7 末）。
   真正的"粘贴/任意宿主文本"处理属于平台前端与后续阶段，本轮不声称支持。
3. **多分隔符词形不支持**：`rock'n'roll`、`co--operate`、`don't-x` 一律只保留原文。
4. **没有 Unicode 弯撇号/破折号规范化，也没有自动标点替换**：
   `'` 与 `U+2019` 是两回事，本轮不做映射，也不把 `don’t` 变成 `don't`。
5. **没有 URL/邮箱/代码解析器**：保护是"见到这些字节就不补"，不是"认出这是一条 URL"。
6. **`iPhone` / `GitHub` 一类专名不补全**（判 mixed 保留原文）；句首自动大写、
   专名大小写恢复、纠错、预测、学习、下一词预测均未实现。
7. **本轮仍以单个无空白 token 为测试单位**：不声称已完成多词输入、粘贴或任意宿主编辑支持。
8. 缓存无热重载（任务书第十节）；`queries_covering_*` 是进程级"最近一次"计数，
   只在单 session 动作后立即读取使用，交错使用只读增量。
9. english 模式的 hook label 文案仍是 `P2.1`（模式标识，不是阶段声明）；
   为改文案需要重新登记已哈希的构建入口，本轮按"够用就复用"没动。
10. 风险：`speller/alphabet` 扩到 76 字节后，任何依赖"alphabet 只含字母"的上游行为都会变。
    本轮核对了 speller / abc_segmentor / fallback_segmentor / editor 四处，
    并且 P1.4 探针 5/5、P1.3 回放 2/2、P1.2 smoke 1/1 都在各自引擎上复跑通过；
    **但这四处不是穷举**。
