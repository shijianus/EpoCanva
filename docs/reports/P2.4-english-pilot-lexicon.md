## 2. 本轮实际做了什么

1. **确定官方来源并固定身份**：用 SourceForge 的项目页与 REST 元数据把"en-wl/wordlist"
   落到唯一的 git 远端，再用 `git ls-remote`/`git tag --points-at`/`git rev-list --count`
   把一个**完整提交**钉下来，并明确记录为什么不用 tag 当身份、不用分支 tip 当恢复点。
2. **读授权正文**，把公有领域声明、致谢请求、以及作者自己写明的 **AGID 例外**
   逐字引到清单与合规文档里，并据此把 AGID 派生文件排除在导出范围之外。
3. **写了转换器**（`tools/data/build_english_pilot.py`）：默认离线、先验证后解析、
   不清洗、逐原因计数、输出确定性、`--check` 要求二次运行逐字节相同。
4. **生成了 pilot 词表**：42,356 行 `word<TAB>weight`，502,333 字节，
   含 69 行撇号词与 1,697 行连字符词。
5. **接入真实引擎**：新增 `--mode pilot-lexicon`，在自己的 fixture/输出/运行目录里，
   用真实按键 API 在同一套断言口径下跑了 205 条检查（候选、提交、保护、恢复、隔离、计数恒等式）。
6. **两条 CTest 用例**并门控注册；另做了 **10 个负向控制**（4 个针对产物断言脚本、
   6 个针对转换器），确认它们"能失败"。

## 3. 关键设计决定与被否决的替代方案

| 决定 | 为什么 | 被否决的替代方案 |
| --- | --- | --- |
| 恢复身份用**完整 commit SHA**，tag 名只作描述 | tag 可被移动/删除；分支 tip 是未发布工作态（实测领先 42 个提交） | 固定 `rel-2018.04.16`（仍可被移动）；固定 `master`（不可复现） |
| 数据清单与 `third_party/sources.lock.json` **分开两份** | 前者记录"测试数据的 provenance"，后者记录"引擎构建输入"。合成一份会让"某个词表文件"看起来像构建依赖 | 往 `packages[]` 里加一条 —— 会让人以为链接或安装了它 |
| 生成数据**不进版本库**，只进 `build/` | 项目许可证未定（§8）+ 再分发问题未决；派生数据可由固定提交重生成 | 把 TSV 提交进 `data/` —— 等于替负责人做了再分发决定 |
| 纳入的词形**必须等于**引擎 `IsDictionaryEntryForm` | 否则会出现"转换出来的词，加载器拒收"的分叉，而加载失败会被当成空词表 | 转换宽一点、加载时再丢 —— 丢词不可观测，正是 §3 诚实条款禁止的 |
| **不清洗**（不 lowercase、不去标点） | 任务书边界 8；也因为清洗会把"来源里有多少不支持词形"这一事实抹掉，而它是下一步能力的度量基线 | 把 `Aachen` 折成 `aachen`（本轮明确写为不做） |
| 权重只当**粗分层** | 字段定义来自 `alt12dicts/README:35-38`；实测取值 2–12，最小值恰为 2 与"多于一步词典"的文件定义相互印证 | 当成词频、或按词频归一化后写入 —— 那是伪造语料数据 |
| pilot 用例**条件注册**而不是 SKIP | 未取源的机器不应看到"静默跳过的 pilot 测试"；路径不对就在配置阶段 FATAL_ERROR | `set_tests_properties(... SKIP_REGULAR_EXPRESSION)`（会把"没数据"伪装成"通过"） |
| pilot schema 与手写 schema **逐字同配置**，只差 4 行 | 只有配置相同，两处的行为差才能归因于数据；这条对比本身写进了夹具 README | 给 pilot 配更大的 `page_size`（会让候选上限的 bug 有藏身之处） |
| 规模数字**只打印不判定** | 时间是机器相关的；把它们写成断言会得到一条随负载翻红的用例 | 给 cold/warm 定阈值（不可复现，也不诚实） |

## 5. 转换契约、首次失败与修掉的缺陷

### 5.1 契约（含单位）

- 行式：`ROW_RE = ^ *(\d+): +(\S+) +(\S+) +(\S+) +(\S+) +(.*)$`，与 `2of12full.txt` 的
  五个数字字段一一对上。
- 长度上限：`MAX_WORD_BYTES = 64`，单位是 **UTF-8 code unit（字节）**，与
  `english_token.h kMaxTokenBytes` / `english_lexicon.h kMaxWordBytes` 是同一个别名值，
  不可能三处各写一个数。
- 输入解码：CRLF 配对先验证（清单记录 53,789 对）→ 去掉 CRLF 后**不得再有裸 CR** →
  再按 7-bit ASCII `errors='strict'` 解码（任何 ≥0x80 字节直接失败退出）。
- 输出：`word\tweight`，按词的 UTF-8 字节升序，LF 结尾、无空尾行、纯 ASCII。
  实测 42,356 行 / 502,333 字节 / 每行恰好 1 个 TAB / 首行 `a\t12` / 末行 `zymurgy\t3`
  / 最长词 23 字节 / 权重集合 `{2,…,12}`；
  词表 sha256 `6e46587d8029d8c9cf17b20d33983d051caa6e5e70a3da6573707d25400aae6b`。
- 无时间戳、无绝对路径、无主机名进产物。这一条不只靠 `--check`（同目录重跑一致）来保证：
  换一个输出目录重转，两份产物的 sha256 仍与已有产物逐字节相同（§8 命令表 #23）。

### 5.1b 排除统计（边界 8 要求"排除原因必须统计"，数字与产物 report JSON 逐项一致）

源 53,789 行 → 纳入 42,356，排除 11,433，**无法解析 0**；`纳入 + 排除 = 源行数` 与
`八类之和 = 排除数` 都是被断言闭合的，不是这里手加出来的：

| 排除原因 | 行数 | 纳入词形 | 行数 |
| --- | ---: | --- | ---: |
| `contains-space` | 6,006 | 纯字母串 | 40,590 |
| `capitalised-letter` | 4,373 | 含撇号 | 69 |
| `digit-or-other-punctuation` | 831 | 含连字符 | 1,697 |
| `more-than-one-delimiter` | 208 | | |
| `leading-or-trailing-delimiter` | 15 | 权重分层 | 2..12（直方图在报告 JSON 里） |
| `non-ascii-byte` | 0 | 词长 | 1..23 字节（上限 64） |
| `word-too-long` | 0 | | |
| `duplicate-word` | 0 | | |

`non-ascii-byte=0` 不是"没检查"：文件是按 7-bit ASCII `errors='strict'` 解码的，
且 `duplicate-word=0` 是**去重计数通道仍然在**（引擎里 `aachen` 类冲突才会走它）。
三个"排除但本可支持"的类别（`leading-or-trailing-delimiter`、`more-than-one-delimiter`、
`capitalised-letter`）合计 4,596 行，正是下一阶段"大小写恢复 / 多分隔符 / 词首符号"
的**工作量基线**：本轮把它们计数而不是消化掉。

### 5.2 第一次转换真实失败

第一次运行 **exit 7**："nothing was accepted"。原因不是数据，是我的缺陷：
`2of12full.txt` 用 CRLF，而解析前没去掉 CR，于是每一行的词都带着尾随 `\r`，
全部落到 `digit-or-other-punctuation`。修法是加"CRLF 配对数与清单一致 + 裸 CR 即失败 +
`errors='strict'` ASCII"三道硬检查（§5.1），并在接受数为 0 时**把整张排除表打到 stderr**
而不是只报"空结果"。这个"退出时打印 tally"的分支使 §5.2 这类漂移以后都能自查。

这条修复没有把问题绕过：exit 7 本身现在是被测试的失败路径之一（见 §7.3 的负向控制）。

### 6.4 受保护文本在 42k 行规模上仍不补全

10 条输入，每条断言四件事：菜单只含整串原文、preedit 逐字等于原文、Return 提交逐字相等、
以及**该 token 在所有帧里 `completion_candidates` 增量为 0**。
清单里混着两类拒绝原因，循环断言的是它们的共同点，分类别计数在 P2.3 模式里单独断言：

```
user@example.com   https://example.com/a?x=1&y=2#z   C:\tmp\file.txt
foo_bar            v1.2                              co-operate.
hel2               don't2                            rock'n'roll        'hello
```

末两条是**多分隔符词形**（不支持），前八条是**保护字符**（受保护）；两条不同路径必须
得到同一个用户可见结果：原样返回、原样提交、绝不补半截。

### 6.5 退格恢复与"查无此词"

- `co-oper` → `co-oper2`（停止补全）→ BackSpace → 恢复补全，且恢复帧恰好重发原有条目。
- `Aachen` 不在清单里（未被清洗的证据）：这是一次**查无此词**，与"被拒绝"是不同的事实，
  引擎仍必须逐字节交回打过的 6 个字符（含大写 A）。断言分开写，防止两种情况在实现里被混为一谈。

### 6.6 会话隔离

第二个 session 上重复同样的动作：`attempts` 仍为 1（"一份词表一次读取"在两个 session 之间成立）、
`translator_constructed>=2`（第二个 session 建的是自己的对象）、`Aachen` 的形状与提交
不受第一个 session 的按键历史影响。

### 6.7 计数恒等式在 42k 行上闭合

```
queries=183  with_index=183  rejected=74  orig=183  compl=567
nomatch=13  mixed=0  notalpha=63  toolong=0  illegal=11  protected=63  nonascii=0  unsup=0
cl=463  ci=83  cu=21  delimited=150  whole=183  part=0
attempts=1 ok=1 fail=0 entries=42356  mod_init=1 mod_fin=0 xl_ctor=4 xl_dstr=3 xl_live=1
api.balance  status 221/221  context 221/221  commit 221/221 -- paired
```

- `rejected = mixed + toolong + notalpha + illegal` → 74 = 0+0+63+11 ✓
- `notalpha = nonascii + protected + unsup` → 63 = 0+63+0 ✓
- `compl = cl + ci + cu` → 567 = 463+83+21 ✓
- `whole + part = queries` → 183 + **0** = 183 ✓（每个 token **整串**到达翻译器）
- `delimited(150) <= compl(567)` ✓，`orig = queries` ✓（每次查询都给了原文候选）
- `xl_live=1` 是终局读数（pilot session 尚未销毁）；"销毁后归零"那条断言属于
  `completion` 模式，pilot **不复述也不声称**已覆盖。

`nonascii=0 / unsup=0` 同样是**预期**：不在 `speller/alphabet` 里的键根本进不了组合区，
真实按键路径不可达，只有核心单测能覆盖这两种分类。这一点在方法学文档 §1 里明写着"引擎侧未验证"。

### 6.8 规模测量（只打印、不判定）

同一次注入里，`per_key` 的分母就是打印在同一行的**注入键数**（11 个探针输入合计 41 键）。
两次独立运行的实测：
| 量 | 运行 A | 运行 B |
| --- | ---: | ---: |
| `scale.cold_path`（建会话 + deploy + 首键，首键那一次 Query 里解析并排序整份 42k 清单） | 18,911 µs | 19,135 µs |
| `scale.per_key`（热索引，41 键，含 Return 提交帧） | 76.17 µs | 76.32 µs |
| `scale.warm_path`（第二个 session 同样动作，索引已缓存） | 1,242 µs | 1,323 µs |

运行 B 的完整输出留在 `build/p24-verify/evidence-pilot.log`；运行 A 是同一会话里更早的一次
standalone 执行，日志文件已被 B 覆盖，A 的三个数字取自当时的实际打印。
两次都通过了同一套 205 条断言，所以差别只在时间。

**测量边界与样本数**（P2.5 收尾时补齐；计时点是测试程序内的 `steady_clock`，
两个边界点之间就是下面写明的调用序列，不含未列出的步骤）：

| 量 | 计时起点 → 终点 | 包含 | 不含 | 样本数 |
| --- | --- | --- | --- | --- |
| `scale.cold_path` | `create_session()` 之前 → 第一个键的**状态读回**之后 | 建会话、`select_schema`（引擎据此构造 Translator，第一次 `Query()` 解析并排序整份 42k 清单）、1 次 `process_key`、1 次 get_status/get_context/get_commit 三连读 | `rime.initialize()`、夹具暂存、`deploy_schema()` 本身（在计时起点之前已完成） | **1 次观测**，不是均值 |

因此 `per_key` 里混着 C API 往返与候选复制的固定开销，它是"这一套读法下每键的墙钟时间"，

两个**单次观测**相减得到，本身也带同样的抖动）。

> **这些数字是 P2.4 那一次引擎与那一次运行的读数。** P2.5 给组件加了空格 Processor，
> 并给 pilot 模式末尾加了两个空格步骤，因此现在重跑同一模式得到的是

> （本机 P2.5 实测：cold 21,500 µs / per-key 83.98 µs over 41 keys / warm 1,259 µs，
> `rime.dll` = `8df580f8…`，2,708,992 字节）。逐项变化与理由见
> `docs/reports/P2.5-english-space-boundaries.md`，不要拿本节的表当当前状态读。

**这些数字不能读成什么**：不是生产基准（一台 Windows x64、一份 42k 试验清单、

### 7.3 断言自身必须能失败

**产物断言脚本（`assert_pilot_output.cmake`）的首两次运行是失败的**，且失败都在脚本里、
不在数据里 —— 三次都是我的断言写错，数据始终一致：

1. `string(JSON … GET)` 把 JSON `false` 渲染成 CMake 的 `OFF`，我却拿去和字符串 `"false"`
   比 ⇒ "FAIL … got 'OFF' want 'false'"。改为先查 `TYPE`（CMake 返回大写 `BOOLEAN`），
   再用 CMake 自身真值判断。
2. 同一次运行里 `TYPE` 比对用小写 `"Boolean"` ⇒ "is a BOOLEAN, not a boolean"。
3. **CMake 的正则引擎不支持 `{n}` 量词**：`^[0-9a-f]{40}$` 把花括号当字面量，于是
   完整 40 位 SHA **匹配失败**。改为"长度恰好 40/64 + 字符类 `^[0-9a-f]+$`"两件事一起查
   （只查字符类会放过 39 位前缀）。脚本里留了这条限制的注释，就是这段发现过程的痕迹。

随后做了 **4 个负向控制 + 1 个对照**（`build/p24-verify/neg_check_output.py`，exit 0）：

```
truncated lexicon                  exit=1 REFUSED as designed      （sha256 + size + 行数）
report tally off by 7              exit=1 REFUSED as designed      （八类之和≠排除数）
report claims zero hyphen rows     exit=1 REFUSED as designed      （pilot 会停止检验 P2.3 词形）
manifest shortened to a 7-char ref exit=1 REFUSED as designed      （浮动引用不被接受）
unmodified pair (control)          exit=0 PASS
```

再做 **6 个转换器负向控制**（`build/p24-verify/neg_check_converter.py`，exit 0，
并核对真实产物哈希在整个过程中未被改动）：

```
no source root, no --fetch                    exit=4  （默认离线可证）
CRLF normalised copy                          exit=5  （解析前逐文件哈希）
manifest CRLF record wrong                    exit=5  （行尾契约变化不被吸收）
truncated mid-line, manifest rewritten        exit=5  （行格式守卫，拒绝猜测）
truncated on a line boundary, manifest rewritten  exit=7  （--check 字节比对）
--check with no stored output                 exit=2  （不误诊为"不确定"）
```

这 10 条都是"能失败"的证据；没有一条是靠 `exit 0` 硬编码的。

## 9. 未完成项与风险

1. **两个授权决定仍未决**（合规文档 §5）：非美法域的再分发结论、打包时致谢的载体形式。
   在这两点定下来之前，pilot 数据不能进任何安装包，也不能提交进仓库。
2. **词表只是拼写清单，不是输入法词库**：权重是"被几部词典收录"的粗分层，
   没有用户语料、没有上下文、没有学习。候选顺序因此**不能**当成生产排序的近似。
3. **AGENTS.md §1 列的其余英文能力一个都没做**：形态变化、纠错、连写切分、
   缩写展开、跨应用一致性、下一词预测全部仍是"未实现"。
   本轮把 `don't`/`co-operate` 从"手写 5 行"推到"真实 69 + 1,697 行"，
   但**没有**实现复数/`-ed`/`-ing` 之类的形态推导。
4. **非 ASCII 与"粘贴文本"仍不可达**：不在 `speller/alphabet` 的键进不了组合区，
   所以 `non-ascii`/`unsupported-byte` 只在核心层有覆盖，引擎侧写"未验证"。
5. **规模数字是单机的**：没有第二台机器复测，也没测更大词表（50k+ 的斜率未知）。
6. **`third_party/wordlist` 取到 `build/` 而不是 `third_party/`**：
   与 §7/§10 一致，但如果以后要把词表升级为**运行时资产**，
   就得为它建正式的登记与（若需要）补丁机制，那是下一阶段的事。
7. **脚手架还没沉淀成可复用工具**：`build/p24-verify/*.ps1|*.py` 是一次性验证脚本，
   本轮**不**晋升进 `tools/`（任务书"不要把 scratch 脚本整体提升"）。其中
   `run_pilot_ctest.ps1` / `regress-all-p24.ps1` 里含本机绝对路径，
   若要复用需先参数化（AGENTS.md §10 禁止提交机器专属路径）。
   已应用过的补丁脚本（`patch_cmake_pilot.py` 等）留在原地作为过程痕迹：
   它们的锚点断言在补丁生效后**必然失败**，因此不会被误重跑成二次插入。

风险清单（下一轮之前不该被遗忘的）：
把粗分层权重当词频；把 pilot 的 `entries=42356` 当"已支持词典"；
用 pilot 时间数字做对外比较；在未决授权问题上先打包。
