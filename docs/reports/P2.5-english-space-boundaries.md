## 0. 实际采用的空格与候选选择语义

三条规则，按 `engine/languages/en/english_space_policy.h` 的命名枚举实现，
由 `engine/rime_components/english/english_space_processor.cc` 执行：

| 规则 | 触发条件（每事件现读，不记忆） | 动作 |
| --- | --- | --- |
| **A** `kCommitTokenThenSpace` | 正在组合，且**没有**任何 segment 的 status ≥ `Segment::kSelected` | 提交 `Context::input()`（原始组合串）→ 清空 → 再提交一个 U+0020 |
| **B** `kCommitSelectionThenSpace` | 正在组合，且已有显式选择待落地 | `Context::Commit()`（引擎自己算已确认组合的提交文本）→ 再提交一个 U+0020 |
| **C** `kSpaceOnly` | 组合为空 | 只提交一个 U+0020 |

明确**不做**的事，且都写成了断言而不是免责声明：

- 默认空格**不接受补全**。高亮（`highlight_candidate`）不算选择：`hel` + 高亮 1 + 空格
  提交的是 `hel `，不是 `hello `。
- 不压缩连续空格、不去首尾空格：空组合连按两次空格得到 `"  "`（两个独立事件）。
- 不跨已提交文本删除或替换；空组合下的 BackSpace **沿用上游语义**（见 §2.4）。
- Ctrl / Alt / Super 组合键与按键抬起**不进入**提交路径，也不被吞掉（返回 `kNoop`，
  事件继续沿链下发）。
- 不保存"上一个词"。Processor **没有任何数据成员**，重复提交在结构上不可达；
  跨 session 也无共享状态。

处理顺序是机制本身：`engine/processors` 里 `epocanva_english_space` 排在
`speller`、`fluid_editor` 之前，因为引擎在第一个非 `kNoop` 处就停止
（`src/rime/engine.cc:99-108`）。非空格键一律 `kNoop` 放行，
所以原有 26 条用例的按键路径**没有任何一个字节**改道。

诊断面新增 11 个计数（追加在结构体末尾，旧字段偏移不变）：
`space_processor_constructed/destroyed/live`、`processor_key_events`、
`space_events_seen`、`space_events_refused`、`space_case_a_raw_token`、
`space_case_b_selection`、`space_case_c_empty`、`composition_commits_issued`、
`space_characters_emitted`。恒等式（由测试断言，不靠文字声明）：

```
space_characters_emitted   = case_a + case_b + case_c
composition_commits_issued = case_a + case_b
space_events_seen          = case_a + case_b + case_c + space_events_refused
processor_key_events       = 测试侧发出的键数
```

## 2. 提交链的核实（先读源码，再写期望）

任务书要求"不要凭旧印象认为 `select_candidate` 只改变高亮"。**核实结果：它确实不是只改高亮，
但它也不提交文本。** 完整链路（全部读自固定提交 `33e78140250125871856cdc5b42ddc6a5fcd3cd4`）：

### 2.1 两个不同的 API 入口，两个不同的 Context 方法

```
src/rime_api_impl.h:1040-1043  RimeSelectCandidate      -> do_with_candidate(..., &Context::Select)
src/rime_api_impl.h:1035-1037  RimeHighlightCandidate   -> do_with_candidate_on_current_page(..., &Context::Highlight)
src/rime/context.cc:118-130    Context::Select    : seg.selected_index = index; seg.status = kSelected; select_notifier_
src/rime/context.cc:132-149    Context::Highlight : 只动 selected_index，发 update_notifier_，status 不变
```

⇒ "选择"与"高亮"在引擎里是两个状态；`HasPendingSelection` 因此看 **status**，
不看 `selected_index`。这正是"高亮不等于接受"能实现的原因。

### 2.2 选择之后文本在哪里

```
src/rime/engine.cc:259-270  ConcreteEngine::OnSelect：seg.Close();
        若 seg.end == input().length() -> status = kConfirmed，
        且 _auto_commit 为 true 才 ctx->Commit()，否则 composition().Forward()
src/rime/gear/editor.cc:41-44  Editor 构造时 set_option("_auto_commit", auto_commit)
src/rime/gear/editor.cc:189    FluidEditor : Editor(ticket, false)   <-- 本方案用的是 fluid_editor
```

⇒ 选完之后：**没有**任何文本提交；段被确认并 `Forward()`，
于是 `HasMenu()` 变 false（back segment 没有 menu），`IsComposing()` 仍为 true
（`context.cc:48-50`：input 非空即算组合中），`get_input()` 仍是打过的原文。
文本真正出去要等到下一次 `Context::Commit()`（`context.cc:18-26` →
`commit_notifier_` → `engine.cc:251-257` `OnCommit` → `sink_`）。

运行侧同一事实的读法（`space-commit` 每一步都在按空格**之前**断言）：
提交队列为空、`raw="don'"`、候选菜单为空。

### 2.3 空格在上游编辑器里本来是什么

```
src/rime/gear/editor.cc:191        FluidEditor 绑 {XK_space,0} -> Editor::Confirm
src/rime/gear/editor.cc:87-90      Confirm = ctx->ConfirmCurrentSelection() || ctx->Commit()
src/rime/gear/key_binding_processor_impl.h:69-76   Keymap::Bind(key, nullptr) => erase
src/rime/gear/editor.cc:32 + :73-84  "noop" 映射到 nullptr，且 editor/bindings 在构造之后加载
```

本方案的 schema 里写着 `editor: bindings: space: noop`（沿用 P1.3 起的无干扰夹具做法），
它的作用不是"把空格绑到一个空动作"，而是**抹掉** fluid_editor 的 space→Confirm 绑定。
⇒ **P2.5 之前，英文方案里的空格按键什么都不做**，`process_key()` 返回 False。
这一点是本轮读源码才发现的，也说明"最小 Processor"确实是填补一个真实缺口，
而不是给已有行为加一层包装。（此前任何阶段都没有对空格下过结论，因此不存在旧结论被推翻。）

同理，`Commit` 从不产生空格字符：上游没有任何"提交后补一个空格"的路径，
`ExpressEditor` 也一样（`editor.cc:207`）。所以规则 A/B/C 必须自有组件承担。

### 2.4 BackSpace 与取消的实际语义

```
src/rime/gear/editor.cc:51-57   仅当 ctx->IsComposing() 才查 keymap
src/rime/gear/editor.cc:58-63   char_handler 分支要求 0x20 < ch < 0x7f
src/rime/gear/editor.cc:192     {XK_BackSpace,0} -> BackToPreviousInput
src/rime/gear/editor.cc:200     {XK_Escape,0} -> CancelComposition (ClearPreviousSegment() || Clear())
```

⇒ 组合为空时 BackSpace 不被引擎处理：`process_key()` 返回 False，
删除动作由宿主应用对它自己的文档做。本轮**只记录并钉住这个语义**，
新增的断言是 `handled=0`、无 commit、`raw=""`、候选 0 项；**不声称**支持跨词撤销。
实测读数：`ev=166 key=0xff08 'BackSpace on an empty composition' handled=0 …
composing=0 … raw="" list= commit=-`。

### 2.5 commit 队列与"消费即清空"

```
src/rime/service.cc:19        Session 构造时 engine_->sink().connect(OnCommit)
src/rime/service.cc:55-58     Session::OnCommit: commit_text_ += commit_text   (累加)
src/rime/service.h:38,46      ResetCommitText() / commit_text()
src/rime_api_impl.h:309-325   RimeGetCommit: 非空则复制并 ResetCommitText()，返回 True；否则 False
src/rime_api_impl.h:1062-1070 RimeGetInput  -> ctx->input().c_str()
```

两个后果，都进了测试设计：

1. **一次空格的两次 sink 会被累加成一个队列条目**，所以"提交了几次"只能看计数，
   不能看文本 —— 这就是 §0 那四条恒等式存在的理由。
2. `get_commit()` **消费**文本：再读一次返回 False。回放器早已按同一事实断言
   （`tools/rime_input_replay/main.cc:441-444`，第二轮读为空），
   本模式则每步都读到空为止，并在最后单独具名断言一次（任务书 item 14）。

原始组合取自 `get_input()`，**不是** `preedit`：后者来自
`Context::GetPreedit()` → `Composition::GetPreedit`，是展示加工结果
（可插入 soft cursor，`context.cc:38-46`）。证据行里 `raw=` 与 `preedit=` 分开打印。

## 3. 关键设计决定与被否决的替代方案

| 决定 | 理由 | 被否决的替代方案 |
| --- | --- | --- |
| 规则放核心层（纯函数），执行放组件层 | 引擎的 `Context`/`Session` 在根工程 Debug 里不存在，规则若写在 Processor 里就**无法单测**；分层后 case 29/30/31 能覆盖全部规则表 | 只在 Processor 里写 if（规则不可单测），或把规则塞进测试回放器（任务书明令禁止） |
| Processor 排在 `speller` 之前 | 引擎链在第一个非 `kNoop` 停止；放后面就永远看不到空格 | 放最后（拿不到事件）、或改 `fluid_editor`（那是上游代码，AGENTS.md §7 禁止） |
| 拒绝组合键时返回 `kNoop`，不返回 `kRejected` | `kRejected` 会**截断**整条链（`engine.cc:104-105`），使别的处理器再也看不到该键 | 返回 `kRejected`（等于吞掉系统组合键） |
| 规则 A 提交 `Context::input()` 而不是 `ctx->Commit()` | `Composition::GetCommitText`（`composition.cc:102-120`）取的是 **selected candidate 文本**；若前端只是高亮，`Commit()` 会把补全当成用户意图接受，违背"默认空格不自动接受补全" | 一律 `ctx->Commit()`（上游语义，会接受高亮项）；或比较 preedit（展示层，单位与内容都不可靠） |
| 规则 B 用 `ctx::Commit()` 而不是自己拼文本 | 让引擎自己算已确认组合的提交文本，组件不复算分段逻辑，也不会出现"组件与引擎各算一份"的分叉 | 组件缓存上一词文本后手工拼接（任务书明令禁止，也是重复提交的来源） |
| Processor **零数据成员** | "不保存上一个词全文"的最强实现方式是没有地方可存；session 隔离因此成为结构属性 | 一个 `last_committed_` 字符串 + 比较（正是任务书点名的修法） |
| 空格字符作为**独立**提交事件发出 | 语义清楚：文本提交与分隔符提交各计一次；也让 `space_characters_emitted` 有独立含义 | 一次 `CommitText(text + " ")`（要组件自己算 text，回到上一条的问题） |
| 复用现有配置与组件（speller/fluid_editor 不动，只加一项） | 任务书要求"优先使用现有配置及组件"；实测原有 26 条用例逐条通过，说明其余键路径未变 | 自建整条 processor 链（重复实现退格/取消/字母归属，风险面远大于收益） |
| 新用例注册进正式 CTest，且不用 `build/` 下的驱动脚本 | 任务书 §八；`ctest --test-dir build/librime-english/test` 一条命令就能看到它 | 只留 scratch（P2.4 的教训：条件注册的可见性要靠具名用例） |

```

composition_commits_issued = case_a + case_b
```

`commit` 的读取次数（249）明显多于 status/context（217），正是"每步把队列读到空"
的必然结果，而且配对平衡成立 —— 这是消费语义被真实执行过的旁证。

## 5. pilot 数据上的连续输入冒烟（§七）

pilot 模式（真实 42,356 行词表）末尾加了**两个**空格步骤，
只做少量、稳定、不与候选细节耦合的连续性检查：

```
ev=226 空格（此前 'inter'）handled=1 composing=0 raw="" commit="inter "
ev=233 空格（此前 'co-op'） handled=1 composing=0 raw="" commit="co-op "
P2.5: two words and two spaces on real dictionary data -> "inter co-op "   ok
断言 239 checked, 0 failed（P2.4 时是 205；+34 全部来自这两步）
```

## 9. 仍未支持的编辑行为（明确清单）

1. **连写切分**：`helloworld` 仍是一个 token，整串原样提交；没有词边界推断。
2. **跨已提交文本的撤销/替换**：空组合 BackSpace 交宿主（§2.4），
   已提交的 `Hello ` 不会被英文组件再改动。
3. **任意光标位置编辑**：只做"当前组合 + 空格"；`set_input`、`delete_input`、
   `backward/delete caret` 一类没有本轮语义。
4. **粘贴与批量文本注入**：未实现，也未验证。
5. **标点智能排版、自动句首大写、自动空格插入**（例如在逗号后补空格）：未实现。
6. **Shift+Space 以外的输入法语义**：Caps Lock / Num Lock 状态**不**改变空格行为
   （核心层显式忽略 lock/shift）；`kForwardMask`/`kHandledMask` 等内部位也不当修饰键。
7. **纠错、预测、学习、形态变化、缩写展开、跨应用一致性**：P2.5 明确不做，
   AGENTS.md §1 的其余英文条目仍未触及。
8. **平台前端**：本轮只在无界面测试前端里验证；TSF/Android 侧的空格键路径未实现，
   因此不声称真机行为已验证。
9. **词表**：仍是测试数据。默认夹具 54 行、pilot 42,356 行，都不进安装包（P2.4 §5）。

## 10. 明确不声称的事

- 不声称 `select_candidate` 会提交文本：源码与运行两侧都证明它此刻不提交（§2.2）。

- 不声称 DLL 字节级可复现，也不研究其时间戳（任务书 §八）。
