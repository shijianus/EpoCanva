## 1. 结论

两个已知失败已修复：

* `windows.tsf_coordinator.observed_compose_retirement`
* `windows.tsf_lab.scenarios`（scenario 5，A/B isolation）

根因不是“测试期望写错”这么简单，也不是“把 `AlreadyOrdinary` 改成 `Finished`”。实际有两层：

1. **产品归因缺陷。** `CompositionWriter::active()` 只要 sink 已收到
   `OnCompositionTerminated` 就返回 false，即使 writer 仍持有 `ITfComposition*`。
   `PumpRetirements` 只凭 `active_composition()==false` 就直接记
   `AlreadyOrdinary`，既不区分“从未有自有组合”“此前已正常结束”“被外部终止”，
   也不记录本次清理是否调用过 `EndComposition`。在基线 `b4dff12` 的时序中，焦点切换
   先让 TSF 终止了组合，Pump 看到 `active()==false`，于是把一次真实的外部终止记成了
   `AlreadyOrdinary`，同时旧字段 `completed` 被当作成功总数。
2. **记账/契约缺陷。** 上一会话草稿把 `completed` 改名为 `settled`，但
   `ResolveRetirementCleanup` 仍用局部 `finish` lambda 直接改计数，绕过了统一的
   `SettleRetirementCleanup`。结果是 `cleanup=Finished` 而 `settled=0`，账本不平。
   同时，旧测试无条件要求 `Finished`，没有按本次操作的调用/通知证据选择期望。

修复后，`Finished` 只能来自本次清理自己发起并成功的 `EndComposition`；外部终止是独立
终态 `TerminatedExternally`；`AlreadyOrdinary` 只表示没有自有组合或此前已由 writer 正常
结束；`Blocked` 原样保留，不自动提交、取消或清空文本。

## 3. 冻结后的语义

`RetirementSnapshot` 现在区分四个终态，每个终态由该次操作自己的证据决定：

| 终态 | 条件 |
| --- | --- |
| `Finished` | 本次清理提交了 `EndOwnedComposition`；该计划的回调实际调用 `EndComposition`；调用返回成功；清理开始时组合仍 live，且 writer 此前没有成功结束它。 |
| `AlreadyOrdinary` | 本次清理没有发出 end 调用；writer 从未拥有组合，或此前已通过正常 `Commit`/`Cancel` 成功结束。 |
| `TerminatedExternally` | 本次清理没有发出 end 调用；存在自有组合且 writer 未结束它；TSF/应用在清理开始前或清理计划等待锁期间终止了它。 |
| `Blocked` | 明确不能执行或执行失败，带具名原因：readonly、permission denied/unknown、Uncertain、range mismatch、lock refused、`EndComposition` 失败、shutdown 时组合仍 live 等。 |

`settled` 是“已有唯一终态归因的清理尝试数”，满足：

```
settled == finished + already_ordinary + externally_terminated + blocked
```

它包含所有 `Blocked`，**不是“清理全部成功”**。`finished` 才是唯一的清理成功计数。
UI 和 shutdown 日志从 `completed` 改为 `settled`，并单独显示 `external`、`end_calls`。

## 4. 实现要点

* `CompositionSink` 增加每次生命周期的终止通知计数；`CompositionWriter` 记录
  `ever_owned`、`ended_by_writer`、`externally_terminated`、end 调用/成功/失败次数。
  这些证据在 `ReleaseCompositionAndSink()` 之后仍然有效。
* `CompositionWriter::ownership()` 返回上述证据；`live` 仍表示“当前持有且未收到终止
  通知”，但归因不再只看它。
* `EndOwnComposition` 在调用前对 `ITfComposition` 和 sink 各做一次本地 `AddRef`；
  即使回调重入并释放成员，调用期间对象仍有效。结果证据来自本次调用，而不是调用后的
  成员指针。
* `PumpRetirements` 在决策前调用 `CaptureCleanupEvidence`，把记录级证据固定下来。
  所有终态转换只经过 `SettleRetirementCleanup`，它有“只终结一次”的 guard，并统一
  更新 `settled` 与四个分类计数。
* `ResolveRetirementCleanup` 按 `EditResult` 的本次操作证据分类：
  `kApplied` 必须同时有 `end_composition_issued` 和成功的 `end_composition_hr`；
  `kCompositionTerminated`/`kNoComposition` 不再被当成成功；其余失败映射到具名
  `Blocked`。
* `cleanup_plan_submitted` 以 `EditResult.session_id != 0` 为准；precheck 拒绝没有
  请求 edit session，不能声称提交过 plan。
* 新增共享契约函数 `RetirementAccountingBalanced` 和
  `RetirementCleanupEvidenceConsistent`；协调器测试、Lab self-test 和 Lab scenario 5
  使用同一契约，不再接受“Finished 或 AlreadyOrdinary 任意一个都算通过”。

## 5. 三种正常归因路径的事件时间线

以下证据行来自测试日志，均为无文本计数/状态。`last_retire` 是退役序号，
`last_plan_id` 是清理 edit session 的 plan session id，`last_notif` 是
“清理开始时/调用后”的终止通知计数。

### 5.1 Finished（本次清理自己成功结束）

来源：`retirement-compose-withheld`；`observed-compose-retirement` 在本环境也走此路径。

```
cleanup=Finished ext_term=0 end_calls=1/0
last_owned=1 last_live=1 last_ext=0 last_ended=0 last_notif=0/0
last_retire=1 last_ctx=1 last_gen=1 last_plan=1 last_plan_id=4
last_end=1 last_hr=0x00000000
retire_settled=1 blocked=0 close=1/1
```

时间线：清理开始时组合 live 且此前未结束 → 提交 `EndOwnedComposition`（plan id 4）→
回调持有本地 COM 引用 → `EndComposition` 返回 `S_OK` → sink 通知计数仍由本次调用
吸收（`ended_by_writer=1`）→ 组合枚举为 0，fixture 文本 UTF-16 长度不变，
`set_text_calls`/`text_mutations` 不增加，`composition_end_calls` 只增加本次的 1 次。

### 5.2 AlreadyOrdinary（此前已正常结束）

来源：`observed-compose-already-ordinary`。组合先通过正常 Return/Commit 结束，再退役。

```
cleanup=AlreadyOrdinary ext_term=0 end_calls=0/0
last_owned=1 last_live=0 last_ext=0 last_ended=1 last_notif=0/0
last_retire=1 last_ctx=1 last_gen=1 last_plan=0 last_plan_id=0
last_end=0 last_hr=0x00000000
retire_settled=1 finished=<unchanged> blocked=<unchanged>
```

时间线：正常 Commit 成功 → writer 记录 `ended_by_writer=1` 并释放组合 → 退役清理看到
`owned=1, live=0, ended=1` → 不提交 plan、不调用 end、不写文本 → `AlreadyOrdinary`。

`retirement-queue-full` 覆盖另一个子情形：两个从未拥有组合的绑定，均无 plan/end，
`already_ordinary=2`。

### 5.3 TerminatedExternally（外部 owner 终止）

来源：`retirement-compose-external-before`（清理开始前终止）与
`retirement-compose-external-pending`（清理 plan 挂起期间终止）。两者都用真实
`ITfContextOwnerCompositionServices::TerminateComposition`，且 helper 只在枚举到
**恰好一个**测试组合时才调用，不会碰其他文档或未知组合。

清理开始前终止：

```
cleanup=TerminatedExternally ext_term=1 end_calls=0/0
last_owned=1 last_live=0 last_ext=1 last_ended=0 last_notif=1/0
last_retire=1 last_ctx=1 last_gen=1 last_plan=0 last_plan_id=0
last_end=0 last_hr=0x00000000
```

时间线：owner 终止 → sink 通知计数 1 → 退役清理看到 `live=0, external=1,
ended=0` → 不提交 plan、不调用 end → `TerminatedExternally`。这正是基线
`AlreadyOrdinary` 失败所对应的时序；现在不会被洗成 ordinary，也不会被算成本次成功。

清理 plan 挂起期间终止：

```
cleanup=TerminatedExternally ext_term=1 end_calls=0/0
last_owned=1 last_live=1 last_ext=0 last_ended=0 last_notif=0/1
last_retire=1 last_ctx=1 last_gen=1 last_plan=1 last_plan_id=4
last_end=0 last_hr=0x00000000
```

时间线：清理开始时 live → 提交 plan id 4 并等锁 → owner 在等待期间终止，通知计数变为
1 → 获锁后的回调看到终止，拒绝且不调用 `EndComposition` → `TerminatedExternally`。
`last_plan=1` 与 `last_end=0` 明确证明“提交过计划，但本次没有结束组合”。

### 5.4 Blocked（保护未退步）

`retirement-compose-permission-denied`：

```
cleanup=Blocked ext_term=0 end_calls=0/0
last_owned=1 last_live=1 last_ext=0 last_ended=0 last_notif=0/0
last_plan=1 last_plan_id=3 last_end=0 last_hr=0x00000000
retire_settled=1 blocked=1
```

`retirement-compose-range-mismatch`（真实外部 edit 改写了组合范围）：

```
cleanup=Blocked ext_term=0 end_calls=0/0
last_owned=1 last_live=1 last_ext=0 last_ended=0 last_notif=0/0
last_plan=1 last_plan_id=3 last_end=0 last_hr=0x00000000
retire_settled=1 blocked=1
```

两者都保持 `finished=0`、`already_ordinary=0`、`externally_terminated=0`、
`last_end=0`，组合仍 live 或范围文本保留；没有 `SetText`、没有 end 调用。
readonly 和 Uncertain 路径沿用原有保护，新增了同一契约断言。

* 人工点击验收仍未执行；本轮只完成无 UI 的 self-test。
* `observed_compose_retirement` 在本环境走 `Finished`；真实焦点切换导致
  “清理前已经外部终止”的时序没有在 Lab 里自然出现。该路径由受控 owner API 测试

  Lab focus 断言冒充。

  observed 路径会先产生外部编辑失效通知，未单独做 Lab 场景。
* 已注册 TIP 的 StrictTsf 正向 admission 仍未覆盖；本轮不涉及注册逻辑。
* 当 TSF 在 `EndComposition` 返回 `S_OK` 的同时又发出终止通知时，writer 以“本次调用
  成功”为权威证据记 `Finished`；不声称能区分 TSF 对自身结束的重复通知与外部通知，
  只保证外部终止在没有成功 end 调用时不会被记成 `Finished`。
* 本轮没有改焦点状态机、输入许可、英文算法、自然键盘或注册逻辑；没有改性能阈值。
