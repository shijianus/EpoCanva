# EpoCanva 隐私威胁模型（P0.1 基线）

适用版本：P0.1 骨架阶段。本文描述**风险面与应对方向**；
除"工具链探针不读写用户数据、不联网"外，绝大多数控制在后续阶段实现，
当前状态在每节末尾明确标注。

本文不使用"绝对安全""永不泄露""不可恢复删除"这类表述。输入法处理用户全部文本，
任何此类承诺都超出可验证范围。

## 1. 关键区分：谁把文字发出去

这是输入法隐私讨论中最容易被混淆的一点，必须分开表述。

| | 数据流向 | EpoCanva 的责任边界 |
| --- | --- | --- |
| **A. EpoCanva 自身传出数据** | 引擎/适配层/后台组件把键入、preedit、commit、剪贴板、字段元数据发送到网络或外部存储 | **完全可控**。这是 ADR 0003 的禁止项，也是本模型的主要防御对象 |
| **B. 目标应用发送用户已上屏的文字** | 用户在浏览器/聊天软件中按下发送，宿主应用把文本发给自己的服务器 | **不可控，也不属于 EpoCanva 的隐私泄露**。文字一经 `CommitText`/`commitText` 即成为宿主进程的普通文本 |

推论：

- EpoCanva 无法"保护"用户不被宿主应用采集——宿主拥有提交后的明文，
  键盘拦截、截屏、辅助功能读取都是宿主机制的固有部分。
  任何"用了 EpoCanva 所以应用拿不到你的密码"的说法都是虚假宣传，禁止出现在文档或界面中。
- EpoCanva 能做且必须做的，是让 **A 类**不发生：不联网、不记录、不学习、不外传。
- **A 与 B 之间的唯一缓冲是"上屏时机"**。因此密码字段的策略要作用在
  学习/日志/持久化侧（写入侧排除），而不是伪装成"不发送"。

## 2. 资产清单

| 资产 | 敏感理由 | 当前位置（P0.1） |
| --- | --- | --- |
| 键入序列（原始） | 可直接还原用户输入 | 不产生、不存储 |
| 组合缓冲（preedit） | 含未完成意图 | 不产生 |
| 已上屏文本 | 含最终内容 | 仅流经内存，不落地 |
| 焦点字段元数据（字段名、窗口标题、控件类型） | 可推断场景（银行、医疗、约会） | 未实现采集 |
| 学习库 / 用户词组 | **长期聚合即画像**：高频词足以推断健康、性取向、雇主、财务状况 | 未实现 |
| 配置与方案选择 | 敏感度较低，但语言/方言选择仍可推断族群 | 未实现 |
| 崩溃转储 | 进程内存快照，**必然包含缓冲内容** | 未接入任何崩溃上报 |
| 诊断日志 | 常被随手写入用户内容 | 未实现日志子系统 |

## 3. 攻击者 / 风险面

### 3.1 日志（Log）

风险：调试日志把 preedit、commit 或字段名写入文件；日志随反馈包被用户上传；
崩溃报告里带着内存中的明文。

应对方向：

- 日志字段白名单制（只允许枚举与计数），禁止自由格式字符串拼接用户内容。
- 反馈导出前做静态脱敏检查 + 提供"导出内容清单"给用户过目。
- 不接入任何第三方崩溃采集 SDK（ADR 0003 第 1 条）。
- 若允许生成本地转储，必须与日志分目录，且默认关闭。

状态：**未实现**（P0.1 无日志子系统）。探针自身只向标准输出打印固定文本，不写文件。

### 3.2 学习库（Learning store）

风险：学习把"用户在密码框里打过的词"写入用户词库；跨应用上下文特征被完整记录；
词库导出文件成为可直接阅读的用户画像。

应对方向：

- **写入侧**过滤：隐私字段（TSF `TATTE_IS_PASSWORD`、Android `visiblePassword`、
  `imeOptions=actionSend` 的敏感变体、平台 `noLearning`/autofill 标志）
  在提交时即不产生学习样本。字段属性判断失败时按"敏感"处理（默认拒绝）。
- 学习样本不保存原始按键序列，只保存归一化后的词形与计数。
- 上下文字段长度与跨度需有显式上限，并在文档中写明上限值。
- 学习库文件权限：仅当前用户可读；Android 侧使用应用私有目录，
  不放在外部存储；Windows 侧放在用户配置目录并声明其内容性质。

状态：**存储与桥接已实现，产品持久写入关闭**。`engine/data_store` 现在是 schema v3：
profile/language 身份、正负摘要、UTC 毫秒衰减、手动词条、v1/v2 迁移、原子写、
`.v2` 迁移备份、`.corrupt` 损坏隔离与显式清除（含跨 profile 的 `DeleteAll`）。
读取与写入分离：`Read` 只需 Normal 字段与当前 target/generation，`Record` 才要求
录制开关；因此暂停记录停止新写入，但既有偏好仍参与排序，设置页明确说明这一点。
`engine/ranking` 的偏好只读接入统一后端的 COMPLETION 候选，原文候选保持首位。
**产品持久写入仍关闭**，因为 TSF 的字段权限判定是一次查询，不是覆盖排队、worker、
确认和持久化的 OS 锁；`ProductLearningWritesPermitted()` 返回 false。
`.corrupt`、`.v2` 与 `.tmp` 都按敏感用户数据处理，显式清除会删除它们，绝不自动恢复。
DACL 只是访问控制，不是加密、匿名化或同用户沙箱；导出副本与系统备份不在删除承诺内。

### 3.2a 神经预测（Neural prediction）

风险：为了"更聪明"而把用户上下文发给远端模型；或在用户不知情时下载权重；
或把大型模型加载进每一个宿主进程，扩大内存与攻击面。

应对方向：

- 默认状态必须是：不下载、不加载、不推理。基础输入与统计排序在没有模型时完全可用。
- 模型权重只在用户明确请求后获取；下载前展示来源、大小与许可；校验 SHA-256；
  失败不得破坏已安装模型；不得静默下载其他模型。
- 敏感字段既不学习，也不向预测器提供上下文；该判断在**调用侧**完成，
  且调用方必须持有当前字段的权限判断。
- 预测结果只作为候选，受 Session 版本、焦点身份与编辑范围校验；
  过期预测必须丢弃，不得回写已提交文本。
- Windows 不把大型模型加载进 TSF DLL；需要独立本地预测进程与严格 IPC（见 3.5）。
- Android 优先"浏览器下载 + 文件选择器导入"，使输入法 APK 可继续不申请
  `INTERNET` 权限。**不得**声称同一 APK 中某个无网络 Activity 能独立撤销整个应用的权限声明。

状态：**推理代码存在，产品未接线，默认不启用**（`engine/neural/lexical_reranker.cc`）。
模型目录、下载器与导入流程**未实现**。

### 3.3 备份与同步（Backup）

风险：用户词库随系统云备份（Android Auto Backup / Google One / Windows 同步设置）
离开设备；导出文件被用户随手放进共享目录；备份加密强度低于用户预期。

应对方向：

- Android：显式决定 `allowBackup` 与 `dataExtractionRules`/`fullBackupContent` 排除规则，
  并对学习库路径做排除；不得默认允许备份。
- Windows：导出为**显式用户动作**，生成时提示"此文件包含你的个人词库"，
  并把导出内容与实际内容对齐展示。
- 同步功能（若未来做）需要端到端加密与密钥管理设计，作为独立 ADR，不默认纳入。

状态：**未实现**。

### 3.4 删除语义（Do not over-promise）

风险：用户以为"清空学习"等于"数据消失"。现实是：备份副本、崩溃转储、
文件系统的未回收块、以及**已经提交给宿主应用因而已到达对方服务器的文字**都不受我们控制。

必须采用的措辞：

> EpoCanva 提供删除本地学习与词库数据的操作。该操作移除我们写入的本地文件与记录；
> 它不影响你此前已输入并被目标应用接收、存储或转发的内容，也不影响你自行导出的副本或系统备份。

禁止使用：不可恢复、彻底粉碎、绝对无法还原、永不泄露。

### 3.5 IPC 与进程边界

风险与两难（对应 ADR 0003 的 Windows 限制）：

- **进程内**（当前 Windows TSF 模型）：引擎跑在宿主进程里，被注入到任意应用。
  好处是无需 IPC；代价是一旦引擎存在联网代码，它借用的是**宿主进程**的身份与权限，
  用户难以归因，Windows 也无法阻止。同时宿主进程可能更宽松地读取我们的内存。
- **进程外**（独立引擎服务）：便于审计、可加权限约束、崩溃隔离；
  代价是必须跨进程传递 preedit 与提交文本，IPC 通道本身成为新的泄露面，
  且延迟直接影响输入手感。

应对方向（若未来引入 IPC）：

- 命名管道/共享内存必须限定为当前用户 + 显式 ACL，禁止匿名可连。
- 消息只承载完成编辑所必需的文本，禁止附带字段名、窗口标题、进程信息。
- 明确不做跨机器监听，且用构建期检查证明（仅本机、仅命名管道）。
- 认证：防止其他进程连入并索取缓冲（会话令牌在进程内生成，不走环境变量）。

状态：**未实现**，且 P0.1 未确定进程内/进程外取向。

### 3.6 外部插件 / 扩展码 / 第三方方案

风险：第三方方案（`.schema.yaml`、Lua/V8 扩展脚本、外部词典）本质上是在我们进程里
执行别人写的代码。若它发起网络请求或写日志，从用户视角仍是"EpoCanva 把我的字发出去了"。

应对方向：

- 扩展代码不得获得网络能力；宿主提供的 API 面里不出现任何 socket/HTTP 入口。
- 加载前校验来源与哈希；对未签名扩展给出显式风险确认。
- 文档中不得声称第三方扩展"受离线策略保护"——只能说 EpoCanva 不向其提供网络 API。

状态：**未实现**（无插件机制；librime 亦未引入）。

### 3.7 依赖与供应链

风险：librime 及其构建工具链、词库来源、未来可能的第三方组件——
被篡改的 tarball、不干净的提交、许可变更、词库本身的授权问题。

应对方向：

- `third_party/README.md` 的规则：完整 40 位 commit + SHA-256 + 许可证文件路径 +
  允许被哪一层链接；改造一律走 `third_party/patches/`。
- **词库授权与代码授权分离**：代码许可通过不代表语料许可通过，需单独登记。
- 禁止 FetchContent/联网 clone，构建机离线可复现。
- 升级依赖需要重新跑补丁与全部测试，并在阶段报告登记。

状态：规则**已写入文档**；P0.1 未引入任何依赖，因此校验脚本与补丁目录**未实现**
（`third_party/` 目前只有 README）。

### 3.8 Windows 特有：权限模型的诚实描述

- TSF DLL 与宿主同权运行，OS 不提供网络阻止。
- 我们能做的检查是：导入表审查（不出现 `ws2_32.dll`、`wininet.dll`、`winhttp.dll`）、
  依赖白名单、代码评审。这类检查能说明"我们的模块没有静态导入网络入口"，
  不能证明"该进程不会联网"，也**覆盖不到运行期动态加载**（`LoadLibrary` + `GetProcAddress`）。
- 因此**不得把导入表检查结果表述为"离线安全已验证"**。
  P0.1 曾对探针二进制做过一次人工 `dumpbin`，其结论仅是"该二进制没有静态网络导入"；
  同一份源码在不同构建标志下依赖列表并不相同（手工 `cl` 只依赖 `KERNEL32.dll`，
  CMake `/MDd` 另依赖 4 个调试 CRT DLL），说明它是构建标志的函数而非安全属性。
  导入表自动化检查**不作为本阶段完成条件**，留待依赖引入后作为一层纵深防御再设计。
- 安装/卸载会改动系统注册表与受保护目录，因此需要管理员权限；
  这属于可用性风险（被恶意安装器仿冒）而非隐私外传风险，需在安装器阶段单独建模。

### 3.9 Android 特有

- 输入法应用可见**所有**输入内容，包括密码框（`InputMethodManager` 的可见密码回调）。
  因此密码字段的处理必须在实现层可验证，而不是靠约定。
- 不申请 `INTERNET` 权限 → 平台强制离线（这是真实保证，可对外表述）。
- 候选窗绘制发生在系统窗口层，注意不要截屏或读取其他应用窗口内容。
- 外部存储与剪贴板读取在近期 API 版本受系统限制，不得尝试绕过。

## 4. 越权 / 滥用场景（非目标，但登记）

- 恶意软件读取输入法进程内存 → 属于宿主环境失守，超出键盘可控范围。
- 用户设备被执法取证 → 我们不提供"抗取证"承诺；缓解手段只有"不落盘 + 可删除"。
- 拼写检查/建议由第三方键盘接管 → 不在本产品范围。

## 6. 下一阶段必须补的洞

1. 引入 librime 前，先把 SHA-256/commit 校验脚本做成构建期硬失败。
2. Windows 引擎形态决策（进程内 vs 进程外）需要单独 ADR，附带延迟实测数据。
3. 隐私字段判定的降级策略（识别失败即视为敏感）需要在 Session 协议里落成可测条目。
4. 日志子系统从第一行代码起就要带白名单校验用例，避免事后清洗。
